# HRCore PoC 検証計画

PoC のスコープ、検証項目、残る技術論点をまとめたドキュメント。

- 最終更新: 2026-08-04
- ステータス: PoC 実装フェーズ

PoC の位置づけ・体制・期間は `PROJECT.md` 5章、設計内容は `SPEC.md`、要件は `REQUIREMENTS.md` に記載する。
本書は PoC 期間中に更新し、PoC 完了時点の結論（採用した方式と捨てた案）を残す。

---

## 1. スコープ

**含む**
- 期間モデル（`daterange` + `EXCLUDE USING gist`、半開区間 `[)`、無期限は upper NULL）
- エンティティ9本（会社／拠点／社員／雇用／組織／組織階層／役職／役職任命／配属）＋ 階層区分マスタ
- 任意時点断面（as-of）クエリ
- 未来日の異動・組織変更（データの入れ方で実現、反映バッチなし）
- 組織階層の展開（recursive CTE、会社混在のフォレスト構造、歯抜けを含む5階層 ＋ 会社相当組織）
- **会社相当組織（`layer_order = 0`）を階層集計から除外できるか**（`is_countable`）。役員の設置先として機能するか
- フルパス5列展開（`org_full_path()`）が現行の見え方を再現できるかの検証
- 階層区分（`layer_order`）を軸にした人員集計（depth との不一致の検証）
- `assignment` のバイテンポラル並行実装と、更新経路の実装可否検証
- kintone 外部システムのアプリ化（Agent を社内サーバー）での読み取り
- 書き込み経路: kintone 変更申請アプリ → 内製 API アプリ層 → HRCore
- 分析クエリ（経年比較・部門別人員推移）
- **ロール分離**（人事・労務／分析／kintone）による非公開属性のアクセス制御
- **FTE 換算**（頭数との併記、主務ベース）
- **職能（マトリクスの横軸）での集計** — 組織軸との直交、複数職能保持による重複計上の確認
- **在籍状況の2軸分解** — 現行7区分（内部・外部 × 在籍・休職・退職 ＋ 入社前）が、在籍状況3区分 ＋ 社員区分 ＋ 期間モデルで表現できるか
- **案A の遡及訂正シナリオ** — 開始日の訂正・期間の挟み込み等が supersede / close でどこまで書けるか（boundary_shift / split プリミティブの要否と形の判断材料。`SPEC.md` 6.2）
- **監査トリガと冪等化** — 行差分トリガ + `SET LOCAL` の伝搬、request_id による二重実行防御（`SPEC.md` 6.3・6.4）
- **全期間供給アプリの as-of クエリ** — 外部システムのアプリ化への `valid_start <= X and (valid_end > X or valid_end = "")` クエリが SQL に正しく翻訳されるか（`SPEC.md` 4.2）
- **結合済み供給ビュー** — 期間交差（`*`）で区間分割した非正規化ビューの実装と行数・性能
- **外部アプリ化のキー仕様** — `record_key` 合成列がアダプタのキー要件・ルックアップの重複禁止要件に適合するか
- ダミーデータ

**含まない**
- 異動シミュレーション（現状運用がない）
- 組織図の描画（必須でなく、現行流用可）
- 兼務工数（kintone 側）
- マネジメント役割（kintone 側）
- RLS による自レコード限定参照（kintone 側のアクセス権で担保。HRCore はテーブル／列単位の制御まで）
- 専用 SaaS 連携（HRCore の切り出し範囲に法対応要件がない）
- 締日スナップショット（案C は本実装フェーズで判断）
- 会社単位の権限分離（不要）
- 実データ移行・現行データの品質検証（本移行フェーズへ。`REQUIREMENTS.md` 6章）

## 2. 確定させる設計事項

1. kintone 外部システムのアプリ化で HRCore を参照でき、既存業務アプリのルックアップ・関連レコード一覧が動くか（現行資産の互換性）
2. 任意時点の組織・人員断面が単一クエリで取得できるか
3. 未来日の異動・組織変更が、反映バッチなしで基準日到達時に切り替わるか
4. `EXCLUDE` 制約で期間重複データが投入時に弾かれるか
5. 案A/B/C の本番方式の判断材料を揃える — 判断基準は「締日以外の任意記録時点の断面を要する業務が実在するか」（`SPEC.md` 2章、2026-08-04 に基準を差し替え）。案B の並行実装は実装可否の証明ではなく、この確認の材料集めと位置づける
6. 分析クエリ（経年比較・部門別人員推移）が実用的な複雑さで書けるか
7. 組織階層の展開が、会社混在のフォレスト構造かつ歯抜けのある5階層で正しく動くか。階層区分での集計と depth での集計の差が意図通りに出るか
8. kintone 変更申請アプリ → API 層 → HRCore の書き込み経路が一周するか
9. 格納形式（`daterange` 1列 vs `date` 2列 + 生成列）のどちらを採るか
10. ~~close + insert の配置（書き込み層 vs DB 関数）~~ — 決定済み（2026-08-04）。DB 関数（時系列プリミティブ）側に置き、業務イベントの組成は TypeScript の API 層が持つ（`SPEC.md` 6.1・6.2）
11. **ロール分離が機能するか** — `hrcore_analyst` / `hrcore_kintone` で `person_demographics` が読めず、公開ビュー（`employee_current`）からは氏名が読めること。ビューが定義者権限で動く前提（`security_invoker = false`）の確認を含む
12. **FTE 換算が実用的に書けるか** — 頭数と FTE を並べた組織別集計。兼務者の二重計上が主務フィルタで避けられるか
13. **マトリクス集計が成立するか** — 「kintone 開発組織の人員」と「全製品のフロントエンドエンジニア」を同じデータから出せるか。組織軸 × 職能軸のクロス集計。複数職能保持による重複が意図通りに現れるか
14. ~~組織側の外部コード対応（`org_external_code`）が必要か~~ — 確認済み（2026-08-04）。bozuman コードは職能側（`job_function.external_code`）にのみ紐づき、組織一覧アプリに対応するフィールドはないため不要と判定し `db/schema.sql` からテーブルを削除した
15. **「人員数」の数え方がフラグで書き切れるか** — 社員数／稼働人員数（`is_employee`）、在籍／配属（`is_active`）、階層集計での会社除外（`is_countable`）、頭数／FTE、入社前の扱い。3つのフラグと期間で意図した数値が出るか
16. **入社前の一覧（`employee_pending`）が情シス連携に使えるか** — 機材準備・アカウント発行の運用に必要な項目が揃っているか
17. **案A の遡及訂正が書けるか** — 開始日訂正・期間の挟み込みを supersede / close + 手書き SQL で通し、boundary_shift / split プリミティブの要否と引数の形を判断する（`SPEC.md` 6.2）
18. **監査と冪等の仕組みが機能するか** — `SET LOCAL app.changed_by / app.request_id` がトリガから読めること、セッション変数なしの経路が `session_user` にフォールバックすること、同一 request_id の再実行が no-op になること（`SPEC.md` 6.3・6.4）
19. **全期間供給アプリへの as-of クエリが動くか** — `valid_end` の空判定を含む kintone クエリがアダプタで SQL に正しく翻訳されるか（`SPEC.md` 4.2）
20. **組織再編の束投入が一周するか** — CSV インポート → 一括承認 → ドライラン（検証レポート） → 1トランザクション適用（`SPEC.md` 6.5）
21. **`record_key` 合成列がキー要件に適合するか** — 外部アプリ化のレコード識別と、ルックアップの重複禁止の両方（`SPEC.md` 4.2）

## 3. 技術的な残る論点

業務判断が必要な論点・移行に関する論点は `REQUIREMENTS.md` 6章・7章に記載する。

**PoC 中に決める**

1. **格納形式** — `daterange` 1列 vs `date` 2列 + 生成列（2章-9）
2. ~~**close + insert の配置**~~ — 決定済み（2026-08-04）。DB 関数（時系列プリミティブ）側に置き、業務イベントの組成・バリデーション・トランザクション境界は TypeScript の API 層が持つハイブリッド構成（`SPEC.md` 6.1・6.2）
3. ~~**`changed_by`・実行主体の認証**~~ — 決定済み（2026-08-04）。API 層がトランザクション冒頭に `SET LOCAL app.changed_by / app.request_id` を発行し、行差分トリガが読んで `change_log` に記録する。セッション変数なしの経路は `session_user` フォールバック（`SPEC.md` 6.3）。PoC では方式の動作を検証する（2章-18）
4. **boundary_shift / split プリミティブの形** — 遡及訂正シナリオ（2章-17）を通して、引数と挙動を固める（`SPEC.md` 6.2）

**本実装フェーズで決める**

5. **記録時間の本番方式** — 案A / B / C の選択。判断基準は「締日以外の任意記録時点の断面を要する業務が実在するか」（`SPEC.md` 2章、`TODO.md` B章の人事確認とセット）
6. ~~**本番の書き込み層**~~ — 決定済み（2026-08-04）。内製 API 層（TypeScript）は本番も存続。Workato を導入する場合も役割は kintone との接続・リトライ・通知に限定する（`SPEC.md` 1章・6章）
7. **組織図の内製** — 必須ではないため後回し。必要になった時点で全期間供給アプリ + カスタマイズビューで実装（`SPEC.md` 4.2）
