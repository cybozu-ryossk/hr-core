# HRCore PoC システム仕様

HRCore（人事データ基盤）の PoC におけるシステム構成・データモデル・設計判断をまとめたドキュメント。

- 最終更新: 2026-08-04
- ステータス: PoC 実装フェーズ（設計方針は確定、詳細は PoC で固める）

プロジェクトの背景・目的は `PROJECT.md`、要件は `REQUIREMENTS.md`、PoC のスコープ・検証項目は `POC.md` に記載する。
**スキーマの単一ソースは `db/schema.sql`。** 本書は設計判断の根拠を扱い、DDL 本体は重複させない。

## 1. システム構成

**読み取りと書き込みが別系統になる。**

```
[読み取り]
  kintone クラウド  ←  Agent（社内サーバー）  ←  PostgreSQL（社内クラウド基盤 IaaS）
    外部システムのアプリ化                          HRCore
    ※ Agent 側のアウトバウンド通信のみで成立（PostgreSQL のインターネット公開が不要）

[書き込み]
  kintone 変更申請アプリ  →  API 実行アプリ層  →  PostgreSQL
                              （PoC では内製。本番は iPaaS = Workato を想定）
```

- **読み取り** — Agent 経由で外部システムのアプリ化により直接参照。API 層を経由しない
- **書き込み** — kintone 側に変更申請アプリを作り、REST API 経由で HRCore を更新する層を通す。PoC では内製アプリを作り、本番は **Workato** への置き換えを想定する
  - Workato 前提だと、更新ロジックをレシピ側に持たせるより **DB 関数に閉じ込めて関数コール1回で済ませる**設計が有利（4.2 参照）。特に案B（バイテンポラル）の close + insert をレシピで組むのは避けたい
- **kintone 側に見せる形** — HRCore 内部は `daterange` で保持し、kintone 表示用のビューで基準日時点の `date` に落とす（外部システムのアプリ化が range 型を扱えないため）
- **kintone 側機能の利用** — ルックアップ・関連レコード一覧・集計・プロセス管理・JS カスタマイズは外部システムのアプリ化アプリに対しても基本的に利用可能

## 2. 時系列モデリング方式

**有効期間（valid time）**
- 精度は `date`（人事は日単位発効。同一日内に複数回の状態変更を区別する必要はない）
- 境界規約は **半開区間 `[)` で統一**
  - 理由: 4/1 に A 組織を抜けて B 組織へ移る場合、`[2025-04-01,2026-04-01)` と `[2026-04-01,)` が隙間なく接続する。閉区間だと 3/31 と 4/1 の書き分けが必要でバグの元になる
- **無期限は upper を NULL**（`'[2026-04-01,)'::daterange`）
- 格納形式は `daterange` 1列を主とし、期間重複を `EXCLUDE USING gist` で DB 保証する
  - kintone 公開ビューでは `lower()` / `upper()` を `valid_start` / `valid_end` の `date` 2列に展開して見せる
  - 逆（`date` 2列で格納し生成列で `daterange` を持つ）でも成立する。PoC で決める

**未来日データ**
- 未来の `valid_start` を持つ行を通常データとして格納する
- 参照側が基準日を指定することで自然に切り替わる。**反映バッチは不要**

**as-of クエリ**
```sql
SELECT * FROM assignment WHERE valid_period @> DATE '2026-04-01';
```

**記録時間（transaction time）の扱い**

締日が存在し、締日時点の断面をクエリで再現したいという要件がある。方式は3案あり、**PoC では A を基本としつつ `assignment` のみ B を並行実装して判断する**（理由は後述）。

- **案A: valid time のみ + 変更ログ**
  - 利点: 1行1事実でシンプル。kintone にそのまま出せる。クエリが1軸
  - 欠点: 遡及訂正すると過去の集計値が変わる。締日に出した数値を再現できない。監査ログ（jsonb 差分）から当時の断面を組み立てるのは実質不可能
- **案B: バイテンポラル（valid time × transaction time）**
  - 利点: 任意の2軸断面が1クエリで再現できる。遡及訂正が完全追跡可能で、本体が履歴になるため監査ログが不要
  - 欠点: 全クエリに `recorded_period @> now()` が必要（忘れると重複行が静かに返る）。更新が close + insert になり、書き込み層に実装が必要。生テーブル直参照を禁止する運用規律が前提
- **案C: 締日スナップショット**
  - 利点: 本体は案A のまま。締日の数値が確実に固定される。実装が最軽量（バッチ1本）
  - 欠点: 締日以外の任意時点は再現不可。差分の存在は分かるが原因（どの訂正か）は追えない

**PoC で A + B 並行にする理由（後付けコストの非対称性）**

- **C の後付けは容易** — テーブル1本とバッチの追加のみ。ただし過去分のスナップショットは作れない
- **B の後付けは重い** — 全テーブルへの `recorded_period` 追加、EXCLUDE 制約の作り直し、更新ロジック全書き換え。さらに移行前の期間は `recorded_period` の開始時刻が不明になり2軸目が機能しない

→ B の可能性が残るなら PoC で1テーブルだけ試すのが安い。特に「書き込み層で close + insert が実装できるか」は PoC でしか分からない。C は本実装フェーズでいつでも足せるため、今は決めない。

## 3. データモデル

### 3.1 エンティティ

HRCore が持つのは以下の13本（`REQUIREMENTS.md` 1章のスコープ原則に従う）。

| エンティティ | 内容 | 備考 |
| --- | --- | --- |
| `company` | 会社（グループ会社含む） | **現状管理できていない領域。新規追加** |
| `location` | 拠点 | **現状管理できていない領域。新規追加** |
| `person` | 個人。転籍をまたいで不変の識別子 | グループ通算入社日を持つ |
| `person_name` | 氏名・氏名カナ（公開） | `person` と 1:1。**3.5 参照** |
| `person_demographics` | 性別・生年月日（非公開） | `person` と 1:1。人的資本開示の指標算出用。**3.5 参照** |
| `employment` | 雇用（person × company × 期間）。社員区分、入社区分、働き方、通勤拠点、届出拠点、アカウント名 | 会社跨ぎは転籍のみで、在籍出向はない → 同時に1社 |
| `employment_status` | 在籍状況（在籍／休職／退職 × 期間）。イベント種別と事由 | **配属とは独立して切れる。3.3 参照** |
| `employment_condition` | 労働条件（所定労働時間・週の勤務日数・固定残業・労働時間管理・給与体系 × 期間） | **FTE 換算の基礎。3.4 参照** |
| `org_unit` | 組織（組織コード、組織名、英語名、所属会社、階層区分） | |
| `org_hierarchy` | 組織階層（親子関係、期間） | 最大5階層。**フォレスト構造**（複数ルート）を許す |
| `position` | 役職（設置組織 × 役職名 × 役職階層 × 期間） | |
| `position_holder` | 役職任命（person × position × 期間） | |
| `assignment` | 配属（person × org_unit × 期間、主務/兼務区分、異動理由） | 兼務工数は持たない（kintone 側） |
| `working_group` | ワーキンググループ（階層外の横断組織） | **組織階層に乗らない。3.3 参照** |
| `working_group_member` | WG メンバー（person × WG × 期間、管理担当者/メンバー） | |
| `job_function` | 職能（フロントエンド／バックエンド／QA／PD マネジメント等） | 現行の「タグ一覧」。**3.6 参照** |
| `person_job_function` | 職能の割当（person × 職能 × 期間、職能マネージャー/メンバー） | 複数職能を持てる |

加えて、時系列を持たないマスタを3本持つ。

- `org_layer` — 組織階層区分（会社／本部／副本部／部／副部／チーム）。`is_countable` フラグを持つ
- `employment_status_type` — 在籍状況の区分（在籍／休職／退職）。`is_active` フラグを持つ。**3.8 参照**
- `employment_type` — 社員区分（現行の「社員区分」フィールドに沿った18種類。代表取締役社長・執行役員・無期雇用・有期雇用・派遣契約・業務委託契約・出向契約 等）。`is_employee` フラグを持つ。**3.8 参照**
- `position_grade` — 役職階層（役員／本部長／副本部長／部長／副部長／チームリーダー）。**`org_layer` と 1:1 対応しない。3.7 参照**

階層区分5段階・歯抜け許容・集計軸の業務ルールは `REQUIREMENTS.md` 3章を参照。

### 3.2 階層の持ち方（隣接リスト格納 + 5列展開ビュー）

現行の kintone 組織アプリは、自分に至る経路を5列に展開した非正規化フルパスを持つ（`REQUIREMENTS.md` 3.4）。HRCore ではこれをどう持つかで3案を検討した。

- **案1: 現行踏襲（5列フルパスを実テーブルに持つ）**
  - 利点: 移行が最も楽。kintone 表示がそのまま。`WHERE level3 = 'EP事業部'` で絞り込め、再帰不要
  - 欠点: **改称・再編で履歴が増幅する。** EP事業本部を1回改称すると、配下の全組織の `level1` を更新することになり、期間を切って**全子孫の履歴行が増える**。実際は1組織の改称なのに、履歴上は配下全組織が変更されたことになる。段数追加に `ALTER TABLE` が必要。親子関係を制約で守れない
- **案2: 隣接リスト + 階層区分のみ**
  - 利点: 改称は `org_unit` 1行、再編は `org_hierarchy` 1行で済み履歴が最小。期間を持つのが「親子関係」であり組織再編の実体と一致する。段数変更にスキーマ変更不要。親子制約をトリガで守れる
  - 欠点: フルパス取得に recursive CTE が必要。kintone にそのまま出せない
- **案3: 格納は案2、kintone 公開は5列展開（採用）**
  - 案2 の履歴効率と制約を得つつ、見せ方だけ現行の5列に合わせる。kintone 側の既存アプリの参照（`level3 = 'X'` 等）を維持できる。段数追加はビューの列追加だけで済む

**採用理由**: 決め手は履歴の増幅。HRCore は組織再編の履歴を正確に持つことが目的なので、案1 の「1組織の改称で配下全組織の履歴行が増える」性質は中核テーブルとして許容できない。kintone 側の見え方は展開ビューで完全に維持できるため、現行の利便性を捨てる必要がない。

**展開時の重要な規則**

**5列の列位置は depth ではなく `layer_order` で決める。** これが歯抜けを正しく `NULL` にする。`org_unit` に `layer_code` を持たせている理由でもある。

`EP事業本部 → EP事業部`（副本部なし）の場合、`level1='EP事業本部', level2=NULL, level3='EP事業部'` が返り、現行の見え方と一致する。

### 3.3 在籍状況とワーキンググループを分離した理由

現行の kintone では「配属(入社・復職・異動・休職・退職含む)管理」アプリが、配属とライフサイクルイベントの両方を持っている。期間モデルではこれを2つの事実に分解する。

**在籍状況（`employment_status`）を `employment` から分けた理由**

`employment` の期間は「雇用契約があるか」しか表せず、休職を表現できない。休職を配属で表そうとすると次のどちらかになり、どちらも壊れる。

- 休職中の `assignment` を消す → 配属履歴が分断され、復職時に同じ配属を再登録することになる
- 何もしない → 在籍人員数に休職者が混ざる

そこで在籍状況を独立した期間として持つ。**休職しても `assignment` は切らない**運用とし、「在籍かつ配属」を数えるときだけ両者を JOIN する。

```
employment_status   p1 在籍 [2020-04-01,2026-06-01) / 休職 [2026-06-01,2026-12-01) / 在籍 [2026-12-01,)
assignment          p1 HRINF true [2022-04-01,)      ← 切らない
```

副作用として、人員集計で `employment_status` の JOIN を忘れると休職者が混ざる。これを防ぐため、**kintone 公開ビュー（`employee_current` / `assignment_current`）には `is_active` を出す**（4.2 参照）。

**イベント種別・事由の置き場所**

在籍イベント（入社・復職・休職・退職）は `employment_status`、異動理由は `assignment` に持つ。1テーブル1事実になり、離職率は `employment_status` だけ、異動率は `assignment` だけで算出できる。「入社」は在籍開始と初回配属の両方に現れるが、この重複は許容する（全イベントを1本の `personnel_event` に集約する案は、状態と履歴の二重管理になり課題②の再発になるため採らない）。

**休職は細分化しない（人事・労務確認、2026-08-04）**

産休・育休・私傷病・介護のいずれも休職中は `is_active = false` で共通のため、`employment_status_type` に個別の状態区分は追加しない。区分が必要になる基準は「その状態が `is_active` の判定を変えるか」であり、この4種はいずれも変えない。一方で `reason` をフリーテキストのままにすると、男性育児休業取得率（3.5 参照）のような開示指標の集計が表記ゆれで漏れる。**`reason` の値は CHECK 制約または小さな参照テーブルで固定し、状態は増やさず理由の値だけ統制する。**

**ワーキンググループを `org_unit` に入れなかった理由**

`org_unit` + `org_hierarchy` は「親は同時に1つ」「`layer_order` が単調増加」を前提にしている。WG は階層外・横断・複数所属なので、この制約に載せると `org_layer` に6段目を足すような歪んだ表現になる。別エンティティ2本（`working_group` / `working_group_member`）で持つ。

### 3.4 労働条件を HRCore に持つ理由と FTE 換算

労務系5項目（所定労働時間数・週の勤務日数・固定残業時間数・労働時間管理・給与体系）を `employment_condition` として HRCore 側に持つ。

**給与体系（`pay_type`）を同居させた理由** — 中身は月給／年俸／日給／時給という賃金の分類だけで、給与額は持たない。機微度が他の4項目と変わらないため別テーブルに分ける必要がない。金額を持たないので人件費のシミュレーションはできず、体系別の人員構成とその推移までが分析範囲になる。

**HRCore に含めた理由**

- 現行では5項目とも「社員名簿(公開)」アプリにあり、**すでに公開情報として扱われている**。スコープ原則（公開情報の骨格のみ）から除外する根拠がない
- **これがないと人員を頭数でしか数えられない。** サイボウズは働き方が多様なため頭数と FTE の乖離が大きく、要件 1.3 の「適切な人員計画・スキル計画」「部門間でのリソース調整」が成立しにくい
- 労働条件の変更履歴は経年分析の対象になる（時短勤務者比率・週4勤務の推移・裁量労働者比率）。kintone に残すと課題①が労務領域で再発する

**`employment` に列として持たなかった理由**

労働条件が変わっても雇用契約は継続する。`employment` に列を足すと労働条件の変更ごとに雇用の期間を切ることになり、「いつからその会社に在籍しているか」が読めなくなる。`employment_status` を分けたのと同じ理屈。

**FTE の分母は `company` に持つ**

`company.standard_weekly_hours`（例: 40.0 = 8時間 × 週5日を 1.0 FTE とする）。会社ごとに所定が異なりうるため会社側に持ち、`employment_condition_current` ビューで FTE を計算して出す。分母を利用側に選ばせると集計がばらつくため DB 側で確定させる。

なお日給・時給者は所定労働時間や週勤務日数が固定でない場合があり、その場合 FTE は実態と乖離する。FTE を使う集計では `pay_type` で対象を絞るか、乖離を前提として扱う。

### 3.5 個人属性を公開度で3テーブルに分けた理由

`person` を識別子・公開属性・非公開属性の3つに分割する。1:1 の分割は正規化のためではなく、**GRANT でアクセス境界を引くための垂直分割**。

```
person              person_id / group_joined_on / created_at      … 識別子。全ロールが参照
person_name         full_name / full_name_kana                    … 公開（組織図・社員名簿に出る）
person_demographics gender / birth_date                           … 非公開（開示指標の算出用）
```

**性別・生年月日を HRCore に持つ理由**

人的資本開示の指標は経年で報告するため、時系列基盤に置く価値が構造的に高い。kintone の非公開マスタに残すと、開示のたびに「当時の組織・役職の断面 × 性別」を手作業で結合することになり、まさに課題①の形になる。

**実際に開示している指標は次の3系統で確定した**（人事・労務確認、2026-08-04）。`person_demographics` に持つべき項目は現状の性別・生年月日の2項目で足り、追加は不要。

- 女性管理職比率 — `person_demographics.gender` × `position_holder` × `position.grade_code`（管理職の線引きは 3.7 参照）
- 男性育児休業取得率 — `gender` × `employment_status`（`reason` = 育児休業）。3.3 で `reason` を持つ決定をしたので HRCore 単体で算出できる
- 年齢構成・平均年齢 — `birth_date` × 基準日
- （参考）勤続年数別の構成 — `person.group_joined_on` で算出（`person_demographics` は不要）

**なぜ3層にしたか（2層でなく）**

氏名は組織図・社員名簿に出る公開情報で、性別・生年月日は非公開。同じテーブルに入れると「公開情報と非公開情報の混在テーブル」になり、テーブル名から機微度が判断できない。ビューの列選別で実用上は防げるが、新規ビューの追加時や定義変更時に漏れる余地が残る。AI エージェントや BI が直接 SQL を投げる前提（`REQUIREMENTS.md` 2.7）では、構造で防ぐ方を選んだ。

**アクセス制御の実現方法（RLS は不要のまま）**

PostgreSQL のビューは定義者の権限で動く（`security_invoker = false` がデフォルト）。したがって公開ビューに `GRANT` すれば、下のテーブルへの権限がなくても氏名は参照できる。

- `hrcore_hr` — 人事・労務。全テーブルの参照・更新
- `hrcore_analyst` — 分析・BI・AI エージェント。全テーブル参照から `person_demographics` だけを `REVOKE`
- `hrcore_kintone` — Agent 経由の kintone。公開ビューのみ

**行レベルセキュリティ（RLS）は依然として不要。** 「自分のレコードだけ見せる」要件は kintone 側のアクセス権が担うため、HRCore 側はテーブル／列単位の制御で足りる。ロール名と粒度は PoC 用の暫定で、本番は社内クラウド基盤側の運用に合わせる。

**公開ビューには非公開属性を出さない。** 開示指標の算出は `hrcore_hr` ロールが `person_demographics` を直接 JOIN する。専用ビューを作る場合も、そのビューを `hrcore_analyst` / `hrcore_kintone` に GRANT しないことを運用規律とする。

### 3.6 職能をマトリクスの横軸として持つ

現行の「タグ一覧」アプリは、開発組織のメンバーを職能（フロントエンドエンジニア／バックエンドエンジニア／QA エンジニア／PD マネジメント等）で横断管理している。「kintone 開発組織の人員」と「全製品のフロントエンドエンジニア」という**マトリクスの横軸**であり、組織ツリーには紐づかない。

`PROJECT.md` 2.6 の「開発本部からの要望・職能カットでの所属表現」の実体がこれ。**配属（`assignment`）の複数持ちでは表現できない** — 職能は組織ではないため `org_unit` にならない。

**適用範囲は現行のまま（開発本部・人事確認、2026-08-04）** — 開発組織のメンバー限定を維持し、営業・バックオフィス等の全社への拡大は行わない。

**`working_group` と分けた理由**

構造はほぼ同じ（person × 横断グループ × 期間 × 役割）だが、性質が違う。

- **ライフサイクル** — 職能は長期安定、WG は発足・解散がある
- **外部コード** — 職能には bozuman システムの組織コードが紐づく（bozuman 側では職能が組織として扱われている）。WG にはない
- **マネジメントライン** — `PROJECT.md` 2.6 の「職能ごとのマネジメントラインの管理」に対応する。`person_job_function.role = 'manager'` で表現する
- 現行の kintone アプリも別（タグ一覧 / ワーキンググループ一覧）

汎用の「横断グループ」1本に統合すればテーブルを2本節約できるが、職能だけに必要な列（外部コード）が WG 行では常に NULL になり、意味の違うものが同居する。分けた方を選んだ。

**外部コードは1列で始める**

`job_function.external_code` に bozuman の組織コードを持つ。現行はタグ一覧アプリに `bozumanシステム組織コード` フィールドが1つあるだけで、複数システムへの対応は現行の要求にない。必要になった時点で `system_name` を持つ別テーブルへ切り出す。

**`org_external_code` は削除した** — 組織側の外部コード対応表として先に作ったが、棚卸しの結果、bozuman コードは職能側（「タグ一覧」アプリ）にのみ紐づいており、「組織一覧」アプリには対応するフィールドが存在しないことを確認した（kintone アプリID:31/33、2026-08-04）。組織側の外部コード対応は不要と判定し、テーブルを削除した。

**集計軸が4本目になる**

`REQUIREMENTS.md` 3.3 の3軸（会社／階層区分／ツリーの深さ）に職能が加わる。職能軸は他の3軸と直交し、同じ人が複数の職能に属しうるため、職能で人数を数えると**組織軸の合計とは一致しない**（1人が複数職能なら重複計上される）。集計時にどの軸かを明示する必要がある。

### 3.7 役職階層と役員の設置先

現行の「役職階層」フィールドの値は以下。数字が小さいほど組織上の上位。

```
0 役員 / 1 本部長 / 2 副本部長 / 3 部長 / 4 副部長 / 5 チームリーダー
```

**`org_layer` と 1:1 対応しない**

1〜5 は `org_layer`（1 本部 / 2 副本部 / 3 部 / 4 副部 / 5 チーム）と数字が対応して見えるが、**1:1 ではない**。副本部長・副部長は「副本部／副部という組織の長」ではなく「**本部／部の No.2**」であり、本部に本部長と副本部長が並ぶ。組織としての「副本部」「副部」は別途存在する。

したがって「設置組織の `layer_order` = `grade_order`」という制約は張れず、`position_grade` は `layer_code` を持たない独立マスタとする。副作用として「部に本部長を設置する」ような矛盾したデータは DB では防げないため、投入時のチェックに委ねる。

**役員は会社相当組織に設置する**

役員は組織階層に属さないが、`position.org_code` は `NOT NULL`。そこで各会社に `layer_code = 'company'`（`layer_order = 0`）の会社相当組織を1つ置き、役員の役職の設置先とする（例: `CB-ROOT` / サイボウズ株式会社）。

この判断から3つの帰結が出る。

1. **階層集計から会社を除外する必要がある。** `org_layer.is_countable` を持たせ、会社相当組織は `false` にする。これがないと「本部レベルの人員数」に会社相当組織が混入する。`employment_status_type.is_active` と同じ、集計側が値を列挙せずフラグで絞るための仕組み
2. **ツリーの深さ上限が 5 → 6 になる。** 本部が会社相当組織の配下に入るため。階層区分の段数（5段）は変わらない
3. **現行の見え方は変わらない。** `org_full_path()` の列位置は `layer_order` 1〜5 で決まるため、会社相当組織（0）は `level1`〜`level5` のどこにも入らない。ただし `depth` は会社を含めて +1 になる

会社相当組織は現行データに存在しないため、移行時に生成する必要がある（`REQUIREMENTS.md` 6章）。

**グループ会社の会社相当組織は配下を持たないことがある**

Cybozu US（`CBUS`）の組織はサイボウズ側のグローバル事業本部の配下にあるため、`CBUS` の会社相当組織は役員設置用の器として存在し、配下組織を持たない独立ルートになる。会社別集計と階層集計が別軸であるという既存の性質（`REQUIREMENTS.md` 3.2）がそのまま現れた形。

**「管理職」の判定は `position_grade.is_management` フラグで持つ方針（線引きの値は未確定）**

女性管理職比率の算出には「どこからを管理職とみなすか」という線引きが必要。技術的には集計クエリ側で `grade_order <= N` と書けば絞れるが、これは「管理職とは何か」という人事制度上の定義をクエリ側にマジックナンバーとして埋め込むことになり、書き手（分析ロール・AI エージェント含む）によって線引きがブレる・誤るリスクがある。

**役職を持たない管理職相当（等級・エキスパート職等）はいないことを確認した**（人事・労務確認、2026-08-04）。したがって管理職の判定は `position_holder`（役職者）を前提にして完結し、別軸を持つ必要はない。

`org_layer.is_countable` / `employment_status_type.is_active` と同じ設計パターンとして、`position_grade` に `is_management` フラグを持たせ、集計側は `grade_order` の具体的な数値を知らなくてもフラグで絞れるようにする方針を採る。**線引きの具体値（チームリーダーを含むか等）は人事確認待ちのため、列追加は確定後にまとめて行う**（`TODO.md` B章）。

### 3.8 在籍状況の7区分を2軸に分解する

現行の「在籍状況」フィールドは7区分。

```
0 入社前 / 1 在籍 / 2 休職 / 3 退職 / 4 在職(外部) / 5 休職(外部) / 6 退職(外部)
```

これは「内部・外部」×「在籍・休職・退職」＋「入社前」の掛け算を1次元に押し込んだもの。1次元のまま持つと区分が増えるたびに組み合わせが増える（出向を足せば「出向(外部)」も必要になる）。HRCore では直交する軸に分解する。

**軸1: 在籍状況（`employment_status`）は3区分**

```
active 在籍（is_active = true） / leave 休職 / retired 退職
```

**軸2: 内部・外部は社員区分（`employment_type`）で表現する**

「外部」は業務委託・派遣などの雇用契約のない外部人材を指す。在籍状態とは直交する属性なので、社員区分側に持つ。マスタに `is_employee` フラグを置き、集計側が区分名を列挙せずに絞れるようにする。

現行の「社員区分」フィールドの選択肢は当初の仮置き（正社員／契約社員／業務委託／派遣の4値）より遥かに細かく、実際は18種類ある（値は `db/schema.sql` の `employment_type` INSERT が単一ソース）。大別すると:

```
雇用契約あり（is_employee = true）: 無期雇用系・有期雇用系・インターン
雇用契約なし（is_employee = false）: 業務委託・派遣・EOR・協力会社・顧問
役員系（is_employee = false）: 代表取締役社長・社外取締役・監査役・執行役員（委任契約と想定）
その他（is_employee 要確認）: 出向契約、ラボユース（契約実態が未確認。`TODO.md` B章参照）
```

**執行役員は一律 `is_employee = false` で確定した**（人事・労務確認、2026-08-04）。使用人兼務型（従業員としての雇用契約を持ちながら執行役員を兼ねる）のケースは実在するが少数であり、人員集計の分母への影響は小さいと判断した。個人ごとの実態を厳密に区別する設計（`employment_type` から `employment` へのフラグ移動）は採らない。

外部人材も `employment` テーブルで扱う。「雇用」という名前と実体はずれるが、現行も同じ名簿で管理しており、配属・職能・WG を同じモデルで扱えるため。区別は `is_employee` で行う。

**これで「人員数」の意味が2つに分かれる**

- **社員数** — `is_employee` かつ `is_active`。人的資本開示の分母はこちら
- **稼働人員数** — `is_active`（外部人材を含む）。組織の実働体制を見るときはこちら

**軸3: 入社前は期間モデルから導出する**

`status` として持たない。`employment.valid_period` の下限が未来日であれば入社前。現行はスナップショット管理だったため状態として必要だったが、未来日データを通常行として持つ方針（2章）の帰結として導出できる。

```sql
SELECT * FROM employment WHERE lower(valid_period) > CURRENT_DATE;
```

`employee_pending` ビューとして公開する（情報システム本部の機材準備・アカウント発行に使う）。`employee_current` は現在断面のビューなので入社前の行は含まれない。

**トレードオフ: 内定辞退の履歴が残らない**

入社前を行の存在で表すため、内定辞退は「未来日の `employment` 行を削除する」ことになり、辞退した事実が残らない。採用管理は HRCore のスコープ外（`REQUIREMENTS.md` 1章）で、HRCore は入社後を扱うと割り切る。`change_log` には DELETE の記録が残る。内定承諾率のような採用分析が必要になった時点で、採用管理側で持つか `employment_status` に `pre_hire` を足すかを判断する。

**集計を絞るフラグが3つ揃った**

同じ設計パターンで、集計側が値を列挙せずに絞れるようにしている。

- `employment_type.is_employee` — 雇用契約があるか（社員数の分母）
- `employment_status_type.is_active` — 在籍として数えるか
- `org_layer.is_countable` — 階層別集計の対象か（会社相当組織を除外）

**⚠ 兼務者の FTE は HRCore 単体では正しく出せない**

FTE を配属（`assignment`）で素朴に集計すると、兼務者が複数組織で二重計上される。正しく按分するには兼務工数が必要で、それは kintone 側にある。HRCore 単体で正しく出せるのは**主務ベースの FTE** のみ。組織別の正確な FTE を出すには kintone との結合が必要になる（`REQUIREMENTS.md` 7章のリスク）。

## 4. スキーマ

DDL 本体は `db/schema.sql`（実行可能な単一ソース）。本章はその構成と、DDL だけでは読み取れない設計判断を記載する。

### 4.1 構成

- **マスタ** — `company` / `location` / `org_layer` / `employment_status_type` / `employment_type` / `position_grade`
- **人** — `person` / `person_name` / `person_demographics` / `employment` / `employment_status` / `employment_condition`
- **組織** — `org_unit` / `org_hierarchy` ＋ 階層区分を検査する制約トリガ `trg_org_layer_order`
- **役職・配属** — `position` / `position_holder` / `assignment`（案A）/ `assignment_bt`（案B）＋ 更新関数 `assignment_upsert()`
- **横断的な所属** — `working_group` / `working_group_member` / `job_function` / `person_job_function`
- **監査** — `change_log`（案A 用）
- **ロール** — `hrcore_hr` / `hrcore_analyst` / `hrcore_kintone` ＋ GRANT（3.5 参照）
- **kintone 公開用** — `org_full_path(date)` / `org_path_current` / `employee_current` / `employee_pending` / `assignment_current` / `employment_condition_current` / `working_group_member_current` / `person_job_function_current`

### 4.2 設計判断

**`btree_gist` は必須** — `EXCLUDE` 制約で等値（`=`）と範囲重複（`&&`）を同一インデックスで併用するため。

**`EXCLUDE USING gist` のキー構成が、そのテーブルの「同時に1つ」の定義になる**

- `employment` — `person_id` ＋ 期間 → 同時に所属する会社は1社（在籍出向なし）
- `employment_status` — `person_id` ＋ 期間 → 同時に1状態（在籍・休職・退職は排他）
- `employment_condition` — `person_id` ＋ 期間 → 同時に1つの労働条件
- `org_hierarchy` — `org_code` ＋ 期間 → 親は同時に1つ
- `assignment` — `person_id` ＋ `org_code` ＋ 期間 → 同一組織への重複配属のみ禁止。**複数組織への同時配属は許す**（マトリクス組織・兼務の表現）
- `position_holder` — `person_id` ＋ `position_id` ＋ 期間
- `working_group_member` — `person_id` ＋ `wg_code` ＋ 期間 → 複数 WG の同時参加は許す
- `person_job_function` — `person_id` ＋ `fn_code` ＋ 期間 → 複数職能の同時保持は許す（フロントエンド兼 QA 等）

**`org_layer` を ENUM でなくテーブルにした理由** — 段の追加・並べ替えに `ALTER TYPE` を要求しないため。`layer_order` を数値で持つことで、集計時に階層区分での比較・ソートができる。`employment_status_type` / `position_grade` も同じ理由でテーブルにしている。

**`employment_status_type.is_active` を持つ理由** — 「在籍人員」を数えるとき、集計側が `status_code IN ('active', ...)` と状態名を列挙せずに済む。状態区分が増えても集計クエリを直さなくてよい。

**`org_layer.is_countable` を持つ理由** — 同じ発想。会社相当組織（`layer_order = 0`）を階層別集計から除外するために使う（3.7 参照）。

**`employment_type.is_employee` を持つ理由** — 同じ発想。雇用契約のない外部人材（業務委託・派遣）を人員集計・開示指標の分母から外すために使う（3.8 参照）。マスタに3つのフラグが揃い、集計条件はすべて「フラグで絞る」形で書ける。

**階層区分トリガは `CONSTRAINT TRIGGER` ＋ `DEFERRABLE INITIALLY DEFERRED`** — 組織再編は「親を差し替える複数行の更新」を1トランザクションで行う。行ごとに即時検査すると、途中の状態（まだ親が旧構成のまま）で弾かれる。コミット時まで検査を遅らせることでこれを回避する。

**`org_full_path()` は基準日を引数に取る** — 1断面だけを対象にするため、期間同士の交差計算が不要になり recursive CTE が単純になる。列位置は `layer_order` で決める（3.2 参照）。

**公開ビューは range を `date` 2列に展開する** — 外部システムのアプリ化が range 型を扱えないため、`lower()` / `upper()` で `valid_start` / `valid_end` に落とす。

**公開ビューに `is_active` を含める** — 休職しても `assignment` を切らない設計（3.3）の副作用として、配属を素朴に数えると休職者が混ざる。`employee_current` / `assignment_current` に `employment_status` を LEFT JOIN して `is_active` を出しておくことで、利用側が JOIN を書かなくても在籍者に絞れる。生テーブルではなくビューを使う動機をここでも作る。

**`assignment_bt` は必ず `assignment_bt_current` 経由で参照する** — 生テーブルを直参照して `recorded_period @> now()` を書き忘れると、重複行がエラーなしで返る。これを運用規律として明示する（案B 最大の欠点）。

**案B の更新ロジックは DB 関数（`assignment_upsert()`）に置いた** — `UPDATE` せず、既存行の `recorded_period` を閉じて新行を INSERT する（append-only）。呼び出し側は関数コール1回で済むため、内製 API から Workato へ置き換える際にロジック移植が不要になる。書き込み層に置く方式との比較は `POC.md` 3章-2 の論点。

### 4.3 schema.sql に未実装の項目

5章の整合性要件のうち、現時点で DDL に落ちていないもの。

- `change_log` へ書き込むトリガ（テーブル定義のみ存在）
- 組織階層の循環参照の検出
- ツリーの深さが5を超えないことの検証
- 有効期間のギャップ検出（在籍中に配属がない期間）。**休職者を誤検知しないよう `employment_status.is_active` で除外する条件が要る**
- 在籍状況と雇用の整合検証（`employment` がない期間に `employment_status` が在籍になっていないか）
- `position_grade` の初期データ（役職階層の段数・名称が未確定）
- `employment_status.reason` の値の統制（CHECK 制約または参照テーブル）。休職理由（産休・育休・私傷病・介護 等）の表記ゆれ防止に必要（3.3 参照）

- ダミーデータの投入スクリプト

## 5. 制約・整合性の要件

- 有効期間の重複禁止（単一であるべきもの: 雇用、在籍状況、組織の親、主務配属など）→ `EXCLUDE USING gist`
- 組織階層に循環参照が発生しないこと（再帰クエリでの検出、または投入時チェック）
- 親組織の階層区分が子より上位であること（`layer_order` の単調増加。段の飛ばしは許容）→ 制約トリガ
- ツリーの深さが6を超えないこと（会社相当組織を含む。階層区分は5段）（recursive CTE での検証、または投入時チェック）
- 役員（`grade_code = 'exec'`）の役職が会社相当組織（`layer_code = 'company'`）に設置されていること
- 会社ごとに会社相当組織が1つ存在すること
- 有効期間の間隙（ギャップ）検出 — 在籍中に配属がない期間の検知。**休職期間は配属を切らない運用なので、`is_active = false` の期間を除外して判定する**
- 在籍状況と雇用の整合 — `employment` が存在しない期間に「在籍」の `employment_status` がないこと
- 組織コードを再利用した場合に別組織として区別できること
- 転籍時に `person_id` が連続すること（社員番号の扱いは `REQUIREMENTS.md` 7章の論点）
