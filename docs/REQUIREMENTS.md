# HRCore 要件定義

HRCore（人事データ基盤）に対するプロジェクト全体の要件をまとめたドキュメント。

- 最終更新: 2026-08-04
- ステータス: PoC 実装フェーズ（要件・設計方針は確定、詳細は PoC で固める）

背景・目的・方針の経緯は `PROJECT.md`、データモデルなどのシステム詳細は `SPEC.md`、PoC のスコープ・検証項目は `POC.md` に記載する。

---

## 1. スコープ原則（重要）

**HRCore は公開情報の骨格のみを持ち、項目を限定して変更頻度を低く保つ。**

これにより運用コストを下げる（スキーマ変更の発生頻度を抑える）。利用者は kintone UI 経由でデータを使える状態（外部システムのアプリ化）なので、利便性は損なわれない。

**HRCore（PostgreSQL）が持つもの**
- 会社・拠点・社員・雇用・**在籍状況**・**労働条件**・組織・組織階層・役職・役職任命・配属・**ワーキンググループ**
- 氏名・氏名カナ（公開）、**性別・生年月日（非公開）**
- 組織コードの外部システム対応表（情報システム本部への連携用）
- それぞれの有効期間

**kintone 側が持つもの**
- 緊急連絡先など、HRCore が持たない非公開情報（現行の社員マスタ（非公開）を維持）
- 兼務工数（変更頻度が高い）
- マネジメント役割（理想／業務／組織／人材／投資）
- 各業務システムの付加情報

kintone 側は外部システムのアプリ化で HRCore の情報を引いた上に、これらの付加情報を足す形で構成する。

**個人属性は公開度で3テーブルに分ける**（`SPEC.md` 3.5）

- `person` — 識別子とグループ通算入社日
- `person_name` — 氏名・氏名カナ（公開）。組織図・分析のたびに kintone と結合するのを避けるため HRCore に持つ。改姓は上書き更新で履歴を持たない
- `person_demographics` — 性別・生年月日（非公開）。人的資本開示の指標を経年で算出するために持つ

**この原則から導かれる帰結**
- 非公開の個人属性は `person_demographics` に分離し、**テーブル単位の GRANT と公開ビューの列選別**でアクセスを分ける。ロールは人事・労務／分析／kintone（Agent 経由）の3つ
- **行レベルセキュリティ（RLS）は不要。** 「自分のレコードだけ見せる」要件は kintone 側のアクセス権が担うため、HRCore 側はテーブル／列単位の制御で足りる
- PoC でダミーデータを使うことに無理がない
- ただし副作用として、人的コスト分析では HRCore（配属）と kintone（兼務工数）の結合が必要になる。課題①の縮小再現になりうるため、HRCore 側に主務/兼務の区分だけは保持して結合を素直にする（7章のリスク参照）

## 2. 機能要件

### 2.1 再構築後も維持すべき要件

現行の kintone ベース構成で得られている価値（`PROJECT.md` 2.5）を、再構築後も失わないことを要件とする。

- **人事施策を「あるべき」を前提に実行できる** — システムのデータモデルが人事制度のボトルネックにならない
- **社員番号キーでの全社的なデータ連携性** — 業務システムだけでなく部門業務やアンケートからも参照できる
- **現場主導の改善サイクルとデータリテラシー** — 業務アプリの改修を各部門が主導できる状態を維持する
- **マトリクス組織の表現** — 職能カットでの所属表現を維持する。現行は組織ツリーとは別の「タグ」として職能を管理しており、**配属の複数持ちでは表現できない**。職能を専用エンティティで持つ（2.5、`SPEC.md` 3.6）

### 2.2 時系列データ管理

最重要要件。現行の課題①（`PROJECT.md` 3章）を解消する。

- 主要なエンティティが**有効期間**を持ち、履歴と現在値を同一のデータとして扱えること
- **任意時点の断面（as-of）**を取得できること。基準日を指定すれば、その日の組織・人員構成が得られる
- **未来日の異動・組織変更**を通常データとして登録でき、基準日の到達により自然に切り替わること（反映バッチを不要とする）
- 期間の重複・ギャップが構造的に発生しないこと（DB 制約で防ぐ）
- **締日時点の断面を再現**できること。締日に出した数値が、その後の遡及訂正によって変わらない形で参照できる
  - 実現方式（valid time のみ／バイテンポラル／締日スナップショット）は PoC で判断する（`SPEC.md` 2章）
- 変更履歴（誰が・いつ・何を変更したか）を追跡できること

### 2.3 組織・組織階層

- グループ会社を含む組織を管理できること（会社・拠点は現状管理できていない領域であり、新規に管理対象とする）
- 組織階層を期間付きで管理し、組織再編の履歴を正確に保持できること
- 階層の展開（ある組織の配下すべて、ある組織のフルパス）が取得できること
- **現行の見え方（フルパス5列）を維持できること** — kintone 側の既存アプリが `level3 = 'X'` のような参照をしているため、この見え方を壊さない
- 詳細な業務ルールは 3章を参照

### 2.4 配属・雇用・在籍状況

- 1人が複数の組織に同時に配属されうる（マトリクス組織・兼務）
- 配属に**主務/兼務の区分**を持つ。兼務工数（割合）は kintone 側で管理する
- 雇用は会社ごとに期間で持つ。会社跨ぎは転籍のみで在籍出向はないため、**同時に所属する会社は1社**
- 転籍をまたいで個人を一意に追跡できること（`person_id` は不変）。転籍後も勤続年数を通算できるよう、グループ通算入社日を保持する
- 役職は「設置組織 × 役職名」で定義し、その任命を期間で持つ。役職には役職階層（役員／本部長／副本部長／部長／副部長／チームリーダー）を持たせる
  - 副本部長・副部長は「本部／部の No.2」であり、同一組織に階層の違う役職が並ぶ（`SPEC.md` 3.7）
  - 役員は組織階層に属さないため、会社相当組織に設置する
- **在籍状況（在籍／休職／退職）を配属とは独立した期間で持つ**
  - 休職しても配属は切らない。復職時に配属を再登録しない
  - 「在籍人員」と「配属人員」は別の数え方になる（2.6、`SPEC.md` 3.3）
  - 現行の7区分（内部・外部 × 在籍・休職・退職 ＋ 入社前）は2軸に分解する（`SPEC.md` 3.8）
- **雇用契約のない外部人材（業務委託・派遣）も同じモデルで扱う**
  - 社員区分に「雇用契約があるか」の区別を持ち、人員集計・開示指標の分母から外せること
  - 「社員数」と「稼働人員数（外部人材を含む）」を区別して数えられること
- **入社前の人を扱えること** — 雇用開始日が未来日の行として登録し、入社日到達で自動的に在籍になる。情報システム本部の機材準備・アカウント発行のために一覧できること
- 在籍イベント（入社・復職・休職・退職）と事由、異動理由を保持する。離職率・異動率の要因分析に使う
- **労働条件（所定労働時間・週の勤務日数・固定残業時間・労働時間管理・給与体系）を独立した期間で持つ**
  - 雇用の期間とは独立して切れる（労働条件が変わっても雇用は継続する）
  - **FTE 換算の基礎になる**（`SPEC.md` 3.4）。頭数と FTE を両方出せること
  - 時短勤務者比率・週4勤務の推移・裁量労働者比率・給与体系別の人員構成を経年で分析できること
  - 給与体系は月給／年俸／日給／時給の分類のみ。**給与額は持たない**（人件費シミュレーションは範囲外）

### 2.5 横断的な所属（ワーキンググループ・職能）

組織階層に属さない所属を期間付きで管理する。ワーキンググループと職能は構造が似ているが、ライフサイクルと意味が違うため別エンティティで持つ（`SPEC.md` 3.6）。

**ワーキンググループ**
- 組織階層に属さない横断グループを期間付きで管理できること
- 1人が複数の WG に同時に参加できる
- メンバーに**管理担当者／メンバー**の役割区分を持つ
- WG はサブ分類を持つ

**職能（マトリクスの横軸）**
- 開発組織のメンバーの職能（フロントエンドエンジニア／バックエンドエンジニア／QA エンジニア／PD マネジメント等）を、組織ツリーとは別の軸で管理できること
- **「kintone 開発組織の人員」と「全製品のフロントエンドエンジニア」の両方を数えられること**（マトリクス管理）
- 1人が複数の職能を持てる（フロントエンド兼 QA 等）
- **職能ごとのマネジメントライン**を表現できること（職能マネージャー／メンバーの役割区分）
- 職能に外部システム（bozuman）の組織コードを対応づけられること

### 2.6 分析・集計

- **経年比較**（例: この3年での離職率推移、部門別人員推移）が実用的な複雑さの SQL で書けること
- **階層区分を軸にした人員集計**ができること（ツリーの深さで数えると歯抜け組織が別レベルに混ざるため。3章参照）
- **在籍人員と配属人員を区別して数えられること** — 休職者は配属を持ったまま在籍状況が休職になるため、在籍状況を絡めない集計は「休職者を含む配属人員」になる
- 離職率・異動率の要因分析ができること（在籍イベントの事由、異動理由を軸にする）
- 標準 SQL / BI ツール / AI エージェントから直接扱える形であること

### 2.7 kintone 連携

- **読み取り** — kintone の外部システムのアプリ化により HRCore を直接参照する。API 層を経由しない
- **既存資産の互換性** — 外部システムのアプリ化したアプリに対して、ルックアップ・関連レコード一覧・集計・プロセス管理・JS カスタマイズが利用できること
- **書き込み** — kintone 側の変更申請アプリから UI 経由で入力し、API 層を通して HRCore を更新する
- HRCore は管理画面を内製しない（UI は kintone 側に寄せる）
- 構成の詳細は `SPEC.md` 1章

## 3. 組織階層の業務ルール

### 3.1 階層区分は5段階、歯抜けを許容する

```
（会社）→ 本部 → 副本部 → 部 → 副部 → チーム
  0        1       2       3     4       5
```

`layer_order` 0 の「会社」は組織階層の段ではなく、**役員の役職を設置するための器**（`SPEC.md` 3.7）。各会社に1つ置き、`is_countable = false` として階層別の人員集計から除外する。実質の階層区分は以下の5段。

```
本部 → 副本部 → 部 → 副部 → チーム
 1       2       3     4       5
```

副本部が存在せず本部の直下に部があるなど、**途中の段を飛ばした構成を認める**。したがって:

- 組織の「階層区分」（本部／副本部／部／副部／チーム）と、ツリー上の「深さ」（depth）は一致しない
  - 例: 本部 → 部 → チーム の構成では、チームの depth は 3 だが階層区分は 5段目
- **人員集計・組織図では depth ではなく階層区分（`layer_order`）で集計する必要がある**。「部レベルの人員数」を depth で数えると歯抜けの組織が別レベルに混ざる
- 制約は「親の階層区分が子より上位である」ことのみ。段の連続性は要求しない（`layer_order` が単調増加であればよい）
- ツリーの深さ上限は6（会社相当組織を含む）。階層区分の段数は5

一次情報の「組織階層は5-7階層」は 3,000人規模企業の一般論。サイボウズの実際の階層区分は上記5段階で運用する。

### 3.2 グループ会社の混在

グループ会社の組織がサイボウズの組織ツリー内に存在する（例: グローバル事業本部の下に Cybozu US）。独立ルートの会社もある。このため:

- 組織階層は会社を跨ぐ単一ツリー ＋ 独立ルートの**フォレスト構造**になる
- **会社別集計と組織階層集計が別軸になる**（グローバル事業本部の人員数に Cybozu US の社員が含まれる）

### 3.3 集計軸の整理（4軸あることに注意）

人員数を数えるとき、以下は互いに一致しない。仕様では毎回どの軸かを明示する。

1. **会社** — 雇用元の会社で数える
2. **階層区分**（`layer_order`） — 本部/部/チーム等のレベルで数える。会社相当組織は `is_countable = false` で除外する
3. **ツリーの深さ**（depth） — 歯抜けにより階層区分とずれる。会社相当組織を含むため現行より +1 になる。集計には使わない
4. **職能**（`fn_code`） — 組織ツリーと直交する横軸。**1人が複数職能を持てるため、職能で数えると組織軸の合計と一致しない**（重複計上される）

さらに在籍状況・社員区分・労働条件が絡むと数え方が分岐する。判定はすべてマスタのフラグで行う。

- **社員数 / 稼働人員数** — 外部人材（業務委託・派遣）を含めるかで変わる。`employment_type.is_employee`（`SPEC.md` 3.8）
- **在籍人員 / 配属人員** — 休職者は配属を持ったまま残るため、`employment_status_type.is_active` で絞るかどうかで変わる（2.4、`SPEC.md` 3.3）
- **頭数 / FTE** — 労働条件（所定労働時間 × 週勤務日数）で換算するかどうかで変わる（`SPEC.md` 3.4）
- **入社前を含めるか** — 雇用開始日が未来日の行を含めるかどうか（`SPEC.md` 3.8）

### 3.4 現行の組織データ構造

現行の kintone 組織アプリは、1レコード = 1組織で、自分に至る経路を5列に展開した**非正規化フルパス**を持つ。

```
EP事業本部
EP事業本部, EP事業副部
EP事業本部, EP事業副部, EP事業部 ...
```

歯抜けは `level2 IS NULL AND level3 IS NOT NULL` として表現されている。HRCore ではこの見え方を維持しつつ格納方式を変える（`SPEC.md` 3.2）。

## 4. 非機能要件

- **規模** — 3,000人規模を想定。月間 50〜80名の異動。組織階層は最大5階層（本部／副本部／部／副部／チーム、歯抜け許容）。グループ会社を含む
- **データ量** — 履歴込みでも人事マスタとしては小規模（数十万行オーダー想定）
- **稼働環境** — 社内クラウド基盤の IaaS 上に PostgreSQL を自前構築。バージョン指定は特になし（range types を利用）
- **拡張** — `btree_gist` は必須（`EXCLUDE` で `=` と `&&` を併用するため）。`ltree` は recursive CTE で代替できるため採用しない方針（最小構成を優先）
- **ネットワーク** — Agent を社内サーバーに置き、Agent 側のアウトバウンド通信のみで kintone クラウドと通信する。PostgreSQL のインターネット公開は不要。現状も同様の構成を利用しており実現性の懸念はない
- **権限管理** — 非公開の個人属性（性別・生年月日）を `person_demographics` に分離し、ロール単位の GRANT で制御する（人事・労務／分析／kintone の3ロール）。**RLS による自レコード限定参照は不要**（kintone 側のアクセス権で担保）。会社単位の権限分離も不要。詳細は `SPEC.md` 3.5
- **バックアップ** — 必要。通常の PostgreSQL ダンプ、または履歴を扱う仕組み
- **監視** — クラウド基盤の標準監視を利用。クエリレベルの監視は仕組みがあれば導入
- **監査** — 変更履歴（誰が・いつ・何を変更したか）の保持。バイテンポラル方式を採る場合は本体が履歴を兼ねる

## 5. 運用体制

- **スキーマ変更・開発** — 人事インフラ部＋エンジニア
- **日々のデータ登録・修正** — kintone 側の変更アプリから UI 経由で入力
- **インフラ運用**（バックアップ・監視・障害対応） — 社内クラウド基盤チーム＋情報システム本部
- **kintone 業務アプリの改修** — 従来どおり各部門主導を維持

HRCore は 1章の原則により変更頻度を低く保つことで、この体制で回せる状態にする（必要に応じて、簡単に変更できる仕組みも検討）。

本番の書き込み層は、PoC の内製 API を継続するか **Workato**（iPaaS）に置き換えるかを本実装フェーズで判断する（`POC.md` 3章-5）。

## 6. 移行要件

移行そのものは PoC のスコープ外（本移行フェーズで実施）。ただし設計判断に影響するため、要件として整理しておく。

### 6.1 現行データの品質検証とクレンジング

`PROJECT.md` 2.4 の人力訂正により、期間重複・ギャップ・兼務工数の合計違反・組織コードの欠損参照が存在する見込み。`EXCLUDE` 制約を入れると移行 INSERT が弾かれるため、**移行工数の大部分がクレンジングになる**。

制約なしのステージングテーブルに現行データを流し、SQL で不整合を洗い出す作業が必要。

### 6.2 組織階層の移行（現行5列 → 隣接リスト）

**当初は名前ベースで親を推定する想定だったが、現行データを確認した結果（kintone「組織一覧」アプリの実データ、2026-08-04）、方針を変える。** 現行369件（現行性=現行）中368件（99.7%）で `親組織の組織コード` フィールドに値が入っており、実運用されていることを確認した。一方で「部」「チーム」の名前には同名重複が複数ある（例:「テクニカルライター部」「プロダクトデザイン部」等が開発本部内で複数箇所に存在）ため、**名前ベースの経路（本部〜チーム列）だけでは親を一意に決定できない。** したがって移行は名前推定ではなく、`親組織の組織コード` をそのまま使う。

```sql
INSERT INTO org_hierarchy (org_code, parent_org_code, valid_period)
SELECT
  s.組織コード,
  NULLIF(s.親組織の組織コード, ''),  -- 空はルート扱い
  s.valid_period
FROM staging s
WHERE s.種別 = '現行';
```

**残る確認事項**:
- 親コードが空だった1件（`最小単位組織 = '試用副部'`）はテスト用データの可能性が高く、移行対象から除外するか要確認
- `組織コード` の値に `occy192` のような自動生成コードと、組織名そのもの（例:「デザイン（kintoneプラットフォーム）」）が混在している。一意性・命名規則の整合を移行前に確認する

### 6.3 在籍状況の7区分から2軸へのマッピング

現行の在籍状況を HRCore の2軸に振り分ける（`SPEC.md` 3.8）。

- `0 入社前` → `employment_status` の行を作らない。`employment.valid_period` の下限を入社予定日にする
- `1 在籍` → `active`
- `2 休職` → `leave`
- `3 退職` → `retired`
- `4 在職(外部)` → `active` ＋ `employment_type` を業務委託／派遣にする
- `5 休職(外部)` → `leave` ＋ 同上
- `6 退職(外部)` → `retired` ＋ 同上

外部人材の内訳（業務委託か派遣か）は現行の在籍状況からは判別できないため、社員区分フィールドか別の情報源から補う必要がある。

### 6.4 会社相当組織の生成

現行の組織一覧には会社相当組織が存在しない。移行時に各会社に1つ生成し、既存の本部をその配下に付け替える必要がある（`SPEC.md` 3.7）。

- `org_unit` に `layer_code = 'company'` の行を会社ごとに作る（例: `CB-ROOT` / サイボウズ株式会社）
- `org_hierarchy` で、現行のルート組織（本部）の親を会社相当組織に変更する
- **役員の現行データを確認した**（kintone「役職一覧」アプリの実データ、2026-08-04）。役職階層「0. 役員」は6件登録されている:
  - サイボウズ本体の役員4件（社外取締役／監査役／取締役／代表取締役社長）は**設置組織が空**。現行に会社相当組織がなく位置を持たせられていないため。移行時はこれらを `CB-ROOT` 配下に付け替える
  - 子会社2社の代表取締役社長（CnC／Labs）は、それぞれの子会社組織（サイボウズ・コネクトシー／サイボウズ・ラボ）に**既に設置されている**。この2件は子会社側の会社相当組織へそのまま付け替えればよい
- グループ会社の会社相当組織は配下を持たない場合がある（Cybozu US の組織はサイボウズ側のツリー内にあるため）

### 6.5 遡及範囲

過去履歴（定期出力していたスナップショット）をどこまで遡って取り込むかを決める必要がある。バイテンポラル方式を採る場合、移行前の期間は記録時間の開始時刻が不明になるため、2軸目が機能しないことに注意（`SPEC.md` 2章）。

### 6.6 社内クラウド基盤の受け入れ条件

バックアップ・監視の標準構成への載せ方について、基盤側との最終確認が必要。

## 7. 業務判断が必要な残る論点

技術的な論点は `POC.md` 3章に記載する。

**PoC 中に決める**

1. **社員区分18種類のうち `is_employee` の判定が微妙な値の実態** — 値そのものは確定した（下記「決定済み」参照）。**執行役員は一律 `is_employee = false` で確定した**（下記「決定済み」参照）。残るのは出向契約・出向契約（官民交流）（雇用元は出向先企業と想定）／ラボユース・ラボユース（研究生）（契約実態不明）。いずれも `is_employee = false` を仮置きしている。実態を確認して確定する（`TODO.md` B章）
2. **FTE の分母（`company.standard_weekly_hours`）** — **会社によって値が違うことは確認できた**（2026-08-04）。サイボウズ本体・Cybozu US・Cybozu Vietnam 等それぞれの具体値は未確認
3. **ロールの粒度** — PoC は人事・労務／分析／kintone の3ロール。本番は社内クラウド基盤側の運用に合わせる
4. **「管理職」の判定基準（線引きの値）** — 女性管理職比率の算出に必要。`position_grade`（役員／本部長／副本部長／部長／副部長／チームリーダー）のどこからを「管理職」とするかの線引きが未確定。役職を持たない管理職相当はいないことを確認済みのため（下記「決定済み」参照）、`position_holder` を前提にした判定で完結する。集計クエリ側にマジックナンバーを埋め込まず `position_grade.is_management` フラグで持つ設計方針は決定済み。列追加は線引き確定後にまとめて行う

**決定済み**

- 氏名・氏名カナは HRCore に持つ（改姓は上書き、履歴なし）。過去断面を旧姓で再現する要件が出た時点で `person_name` に期間を足す
- 休職中も配属は切らない。在籍状況を独立した期間として持つ（`SPEC.md` 3.3）
- 在籍イベントは `employment_status`、異動理由は `assignment` に持つ
- **労務系5項目（労務系4項目 ＋ 給与体系）は `employment_condition` として HRCore に持つ**（`SPEC.md` 3.4）。現行で公開アプリにある項目であり、FTE 換算の基礎になる。給与体系は分類のみで金額は持たない
- **性別・生年月日は `person_demographics`（非公開）として HRCore に持つ**（`SPEC.md` 3.5）。生年月日は日まで保持する。個人属性を公開度で3テーブルに分割し、GRANT でアクセス境界を引く
- **職能（現行のタグ）は `job_function` / `person_job_function` として HRCore に持つ**（`SPEC.md` 3.6）。マトリクスの横軸であり、配属の複数持ちでは表現できない。1人が複数職能を持てる。ワーキンググループとは別エンティティにする
- **役職階層は `position_grade` の独立マスタとする**（`SPEC.md` 3.7）。副本部長・副部長は「本部／部の No.2」なので `org_layer` と 1:1 対応せず、`layer_code` は持たせない
- **役員は会社相当組織（`layer_code = 'company'`）に設置する。** `org_layer` に `layer_order = 0` を追加し、`is_countable = false` で階層集計から除外する。ツリーの深さ上限は 6 になる
- **在籍状況は3区分（在籍／休職／退職）に分解する**（`SPEC.md` 3.8）。現行7区分のうち「外部」は社員区分（`employment_type.is_employee`）へ、「入社前」は期間モデルからの導出へ振り分ける
- **雇用契約のない外部人材も `employment` で扱う。** 現行も同じ名簿で管理しており、配属・職能・WG を同じモデルで扱えるため。人員集計・開示指標の分母からは `is_employee` で外す
- **社員区分（`employment_type`）の値は実際の18種類に確定した。** 正社員／契約社員／業務委託／派遣という当初の仮置きは大きく外れていた。値: 代表取締役社長・社外取締役・監査役・執行役員・顧問・無期雇用またはそれに準ずる・無期雇用（チャレンジド）・有期雇用（契約社員）・有期雇用（アルバイト）・インターン・ラボユース・ラボユース（研究生）・派遣契約・業務委託契約・EORサービス契約・出向契約・出向契約（官民交流）・協力会社社員。外部人材の内訳（業務委託／派遣／協力会社／EOR）は社員区分の値から判別できる見込み（`db/schema.sql` 反映済み）
- **労働時間管理（`worktime_mgmt_type`）・給与体系（`pay_type`）は `text` のままとし、マスタテーブル化しない。** 値の妥当性は入力側（API 層）でバリデーションする。労働時間管理は管理監督者（月給）／通常の労働時間制（月給・時給・日給）／裁量労働制（月給）／フレックスタイム制（月給）の6種、給与体系は月給／年俸／日給／時給の4種で確定
- **性別（`gender`）は `男`/`女` の2値。** マスタテーブル化しない
- **組織側の外部コード対応（`org_external_code`）は不要と判定し、テーブルを削除した。** bozuman の組織コードは職能側（`job_function.external_code`）にのみ紐づいており、組織一覧アプリに対応するフィールドは存在しない
- **転籍時の社員番号（`employee_no`）は会社ごとに新規発番される。** `person_id` は不変のまま、`employee_no` は転籍のたびに切り替わる
- **休職は状態（`employment_status_type`）として細分化しない。** 産休・育休・私傷病・介護は全て `is_active = false` の「休職」で統一し、`reason` の値を固定（CHECK 制約または小さな参照テーブル）して集計時の表記ゆれを防ぐ
- **同一役職への複数人就任がある（共同部長等）。** `position_holder` の `EXCLUDE` は現状の `(person_id, position_id, period)` を維持し、変更しない
- **職能（タグ）の適用範囲は現行のまま（開発組織のメンバー限定）。** 全社への拡大は行わない
- **採用分析（内定承諾率等）は不要。** 現行方針（入社前は雇用開始日が未来日の行、内定辞退は行の削除で履歴を残さない）を維持する
- **人的資本開示で実際に出している指標は3系統に確定した。** 女性管理職比率／男性育児休業取得率／年齢構成・平均年齢。`person_demographics` は現状の性別・生年月日の2項目で足り、追加項目はない
- **「管理職」の判定基準は `position_grade.is_management` フラグで持つ設計方針を採る。** 集計クエリ側の `grade_order <= N` のようなマジックナンバーを避け、`is_active`/`is_countable` と同じパターンで判定条件をマスタ側に固定する。線引きの具体値（どの `grade_order` から管理職か）は人事確認待ちのため、列追加は確定後に行う
- **役職を持たない管理職相当はいない。** 等級・エキスパート職のような別軸は不要で、管理職の判定は `position_holder` を前提にして完結する
- **執行役員は一律 `is_employee = false` で確定した。** 使用人兼務型（雇用契約あり）のケースは実在するが少数で、人員集計の分母への影響は小さいと判断し、個人単位の厳密な判定は採らない
- **役員の現行データを確認した。** 役職一覧アプリの実データで役職階層「0. 役員」が6件登録されている。詳細と移行方針は6.4章を参照

**リスクとして認識しておく**

13. 兼務工数を kintone 側に分離したことで、人的コスト分析では HRCore（配属）と kintone（工数）の結合が必要になる。課題①「分析時に結合作業が必要」の縮小再現になりうる。HRCore 側に主務/兼務区分を持たせて結合を素直にするが、分析要件が高度化した場合は工数を HRCore 側に移す判断も検討対象
14. **組織別の FTE も同じ制約を受ける。** FTE を配属で素朴に集計すると兼務者が二重計上される。HRCore 単体で正しく出せるのは主務ベースの FTE のみで、按分には kintone の兼務工数が必要（`SPEC.md` 3.4）
15. 休職者が配属を持ったまま残るため、人員集計で在籍状況の JOIN を忘れると休職者が混ざる。公開ビューに `is_active` を出して緩和するが、生テーブルを直接集計する経路では起こりうる
16. **非公開属性の分離は GRANT の運用に依存する。** テーブル分割は境界を明示するだけで、新しく作ったビューを誤って分析ロールに GRANT すれば漏れる。ビュー追加時に GRANT 対象を確認する運用規律が前提（`SPEC.md` 3.5）
17. **集計軸が4本になり、数え方の分岐が増えた。** 会社／階層区分／深さ／職能に加えて、在籍か配属か、頭数か FTE かで結果が変わる。同じ「人員数」という言葉が複数の値を指すため、レポートや分析クエリでは軸と条件を明示する運用が必要（3.3）
18. **役職階層と組織階層の整合を DB で守れない。** `position_grade` が独立マスタなので「部に本部長を設置する」ようなデータが投入時に弾かれない。組織階層側（`trg_org_layer_order`）は制約トリガで守れているのと対照的で、こちらは投入経路のチェックに委ねる（`SPEC.md` 3.7）
19. **内定辞退の履歴が残らない。** 入社前を「雇用開始日が未来日の行」で表すため、辞退は行の削除になる。採用管理は HRCore のスコープ外と割り切るが、内定承諾率のような採用分析が必要になった時点で方式の見直しが要る（`SPEC.md` 3.8）
