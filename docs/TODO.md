# HRCore 確認待ち事項

現行の運用・データを確認しないと確定できない事項の一覧。

- 最終更新: 2026-08-04
- 対象フェーズ: PoC 実装

確認が済んだら、結果を `REQUIREMENTS.md` 7章・`SPEC.md`・`db/schema.sql` に反映し、この文書の該当項目にチェックを入れて「確認済み」に移す。論点そのものの詳細は `REQUIREMENTS.md` 7章、検証項目は `POC.md` 2章を参照。

## A. 現行 kintone アプリを見れば分かること

自分で確認できるもの。優先度が高い（他の判断の前提になる）。

- [ ] **外部人材の内訳をどこから取るか** — 在籍状況の「在職(外部)」だけでは業務委託か派遣かが判別できない
  - `社員区分` フィールドの選択肢に「業務委託契約」「派遣契約」「協力会社社員」「EORサービス契約」が存在することは確認できた（下記「確認済み」参照）。社員区分から内訳を判別できる見込みが高い
  - `raw/` に投入された生データ（役職・組織・タグ）には社員名簿のデータが含まれておらず、依然未確認。社員名簿の生データが必要
  - 反映先: `REQUIREMENTS.md` 6.3（移行マッピング）

- [ ] **`employee_no` のグループ全体での一意性** — 会社ごとに発番されるため制度上の保証がない。社員名簿の生データで衝突の有無を確認する
  - 設計側は「同時に存在する重複」を `EXCLUDE (employee_no WITH =, valid_period WITH &&)` で禁止する方針（`SPEC.md` 4.2 のキー設計）。業務ルックアップキーとして継続利用するため、全体一意性の実態確認が必要
  - 反映先: `db/schema.sql`（`employment` への EXCLUDE 追加）、`SPEC.md` 4.2

## B. 人事・労務に確認すること

運用ルールの確認。データを見ても分からないもの。

- [ ] **「管理職」の判定基準（線引きの値）** — 女性管理職比率の算出に必要。`position_grade`（役員／本部長／副本部長／部長／副部長／チームリーダー）のどこからを「管理職」とするか
  - **役職を持たない管理職相当はいないことを確認した**（人事・労務確認、2026-08-04）。等級・エキスパート職のような別軸は不要で、`position_holder` を前提にした判定で完結してよい
  - 残る論点は「どの `grade_order` から管理職とみなすか」の線引きの値のみ。集計クエリ側に `grade_order <= N` のようなマジックナンバーを埋め込むとブレる・誤るため、`position_grade.is_management` フラグで持つ設計方針は決定済み（`is_active`/`is_countable` と同じパターン）
  - 列自体の追加は線引き確定後にまとめて `ALTER TABLE` する（2026-08-04 時点では見送り）
  - 反映先: `SPEC.md` 3.5、3.7、`POC.md` 2章、`db/schema.sql`

- [ ] **社員区分18種類のうち、雇用契約の有無（`is_employee`）の判定が業務的に微妙な値の実態** — 一般的な基準で仮置きしたが要確認
  - **執行役員は一律 `is_employee = false` で確定した**（2026-08-04）。使用人兼務型（雇用契約あり）のケースは実在するが少数で、人員集計の分母への影響は小さいと判断し、個人単位の厳密な判定は採らない
  - 残る要確認: 出向契約・出向契約（官民交流）（雇用元は出向先企業と想定して `is_employee = false` を仮置き）／ラボユース・ラボユース（研究生）（契約実態不明のため `is_employee = false` を仮置き）
  - 反映先: `db/schema.sql` の `employment_type` INSERT の `is_employee` 列

- [ ] **締日以外の「任意の記録時点」の断面を要する業務が実在するか** — 記録時間の方式（案A + 案C か、案B か）の判断基準（`SPEC.md` 2章、2026-08-04 に基準を差し替え）
  - 締日（月次・期末・開示基準日）の再現だけで足りるなら案A + 案C で確定。「当時どう記録されていたか」を締日以外の時点で遡って問う業務（訂正をめぐる調査等）が実在するなら案B
  - 反映先: `SPEC.md` 2章、`POC.md` 3章-5

- [ ] **再入社時の `group_joined_on`（グループ通算入社日）の扱い** — 維持（初回入社日のまま）か、再計算（中断を除いた通算の起点）か
  - 再入社は同一 `person_id` 継続・人事の明示紐付けで決定済み（`SPEC.md` 3.5）。残るのは通算ルールのみ。通算の定義次第では「通算勤続」を導出値にする設計変更もありうる
  - 反映先: `SPEC.md` 3.5、`db/schema.sql` の `person.group_joined_on` コメント

## 確認済み

同じ検討を繰り返さないための記録（`PROJECT.md` 5.2 の方針）。

- **役職階層の値** — 0 役員／1 本部長／2 副本部長／3 部長／4 副部長／5 チームリーダー。数字が小さいほど組織上の上位
- **副本部長・副部長の意味** — 「副本部／副部という組織の長」ではなく「**本部／部の No.2**」。同一組織に階層の違う役職が並ぶため、`org_layer` と `position_grade` は 1:1 対応しない
- **在籍状況の現行7区分** — 0 入社前／1 在籍／2 休職／3 退職／4 在職(外部)／5 休職(外部)／6 退職(外部)。「内部・外部」×「在籍・休職・退職」＋「入社前」の掛け算
- **在籍状況の「外部」の意味** — 業務委託・派遣などの雇用契約のない外部人材（グループ会社の社員ではない）
- **タグ（職能）の用途** — 開発組織メンバーの職能（フロントエンド／バックエンド／QA／PD マネジメント等）を組織ツリーとは別の横軸で管理するもの。「kintone 開発組織」と「全製品のフロントエンドエンジニア」のマトリクス管理
- **給与体系の中身** — 月給／年俸／日給／時給の分類のみ。**給与額は含まない**
- **労務系5項目の現行の格納場所** — 所定労働時間数・週の勤務日数・固定残業時間数・労働時間管理・給与体系はすべて「社員名簿(公開)」アプリ。現行で公開情報として扱われている
- **兼務工数** — HRCore のスコープ外。kintone 側で継続管理する（変更頻度が高い）
- **在籍出向** — 存在しない。会社跨ぎは転籍のみなので、雇用は同時に1社
- **社員区分の値**（kintone スペースID:5 / アプリID:34、2026-08-04 確認）— 実際は18種類。正社員／契約社員／業務委託／派遣という仮置きは大きく外れていた。代表取締役社長／社外取締役／監査役／執行役員／顧問／無期雇用またはそれに準ずる／無期雇用（チャレンジド）／有期雇用（契約社員）／有期雇用（アルバイト）／インターン／ラボユース／ラボユース（研究生）／派遣契約／業務委託契約／EORサービス契約／出向契約／出向契約（官民交流）／協力会社社員。`db/schema.sql` の `employment_type` に反映済み。`is_employee` の真偽は役員・出向・顧問等で判定が業務的に微妙なため一般的な基準で仮置き（B章に確認事項を追記）
- **労働時間管理の値**（アプリID:34、2026-08-04 確認）— 管理監督者（月給）／通常の労働時間制（月給・時給・日給）／裁量労働制（月給）／フレックスタイム制（月給）の6種。事業場外みなしは無かった。`text` のままとし、値の妥当性は入力側（API 層）でバリデーションする
- **給与体系の値**（アプリID:34、2026-08-04 確認）— 月給／年俸／日給／時給の4種で確定（想定通り）。`text` のままとし、入力側でバリデーションする
- **性別の値**（アプリID:35、2026-08-04 確認）— `男`/`女` の2値（RADIO_BUTTON）。`M`/`F` 等の表記はない
- **組織一覧の外部システムコード**（アプリID:31/33、2026-08-04 確認）— 「組織一覧」（33）には bozuman コード用フィールドが無い。「タグ一覧」（31）にのみ `bozumanシステム組織コード` フィールドが存在する。`org_external_code` テーブルは不要と判定し削除した
- **転籍時の社員番号**（人事・労務確認、2026-08-04）— `employee_no` は会社ごとに新規発番される（`person_id` は不変のまま `employee_no` は転籍のたびに切り替わる）
- **休職の細分化**（人事・労務確認、2026-08-04）— 産休・育休・私傷病・介護は状態（`employment_status_type`）としては分けない。全て `is_active = false` の「休職」で統一し、`reason` の値を固定（CHECK 制約または小さな参照テーブル）して集計時のブレを防ぐ方針
- **同一役職への複数人就任**（人事・労務確認、2026-08-04）— 共同部長のような運用が**ある**。`position_holder` の `EXCLUDE` は現状の `(person_id, position_id, period)` を維持し、複数人の同時就任を許す（変更不要）
- **採用分析**（人事・労務確認、2026-08-04）— 不要。現行方針（入社前は「雇用開始日が未来日の行」、内定辞退は行の削除で履歴を残さない）のまま
- **人的資本開示で実際に出している指標**（人事・労務確認、2026-08-04）— 女性管理職比率／男性育児休業取得率／年齢構成・平均年齢の3系統。`person_demographics` は現状の性別・生年月日の2項目で足りる（追加項目なし）
- **職能（タグ）の適用範囲**（開発本部・人事確認、2026-08-04）— 現行のまま（開発組織のメンバー限定）。全社への拡大はしない
- **役員が現行の役職一覧に登録されているか**（`raw/positions.json` 実データ確認、2026-08-04）— 登録されている（役職階層「0. 役員」が6件）。サイボウズ本体の役員4件（社外取締役／監査役／取締役／代表取締役社長）は設置組織が空。子会社2社（サイボウズ・コネクトシー／サイボウズ・ラボ）の代表取締役社長2件は、それぞれの子会社組織に既に設置されている
- **組織一覧が経路を組織「名」で持っているか「コード」で持っているか**（`raw/organizations.json` 実データ確認、2026-08-04）— `親組織の組織コード` フィールドが実運用されている（現行369件中368件で充足）。一方「部」「チーム」の名前には同名重複が複数あり、名前ベースの経路だけでは親を一意に特定できない。移行は `親組織の組織コード` をそのまま使う方針に変更した（`REQUIREMENTS.md` 6.2）
  - ⚠ このとき使った `raw/organizations.json` には構造破損が2箇所あった（1件のレコードでフィールド値が途中欠落／別の1件相当が閉じ括弧の重複で消失の疑い）。復旧して459件（現行369／廃止90）で分析したが、正確な件数を使う最終判断の前に再エクスポートを推奨
