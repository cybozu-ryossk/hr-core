## A. 現行 kintone アプリを見れば分かること

自分で確認できるもの。優先度が高い（他の判断の前提になる）。

- [ ] **社員区分の値** — 「社員名簿(公開)」の `社員区分` フィールドの選択肢
  - 現在 `employment_type` に 正社員／契約社員／業務委託／派遣 を仮置きしている
  - 反映先: `db/schema.sql` の `employment_type` の INSERT、`is_employee` の真偽

- [ ] **外部人材の内訳をどこから取るか** — 在籍状況の「在職(外部)」だけでは業務委託か派遣かが判別できない
  - `社員区分` フィールドに入っているか、別アプリか
  - 反映先: `REQUIREMENTS.md` 6.3（移行マッピング）

- [ ] **労働時間管理（`worktime_mgmt_type`）の値** — 「社員名簿(公開)」の `労働時間管理` フィールドの選択肢
  - 通常／裁量労働／管理監督者／事業場外みなし 等が想定されるが未確認
  - 決めること: `text` のままにするか、`org_layer` と同じ形のマスタにするか

- [ ] **給与体系（`pay_type`）の値** — 月給／年俸／日給／時給と聞いているが、選択肢の正確な表記
  - 決めること: マスタ化するか `text` のままか

- [ ] **性別（`gender`）の値** — 「社員マスタ(非公開)」等での持ち方（`男`/`女`、`M`/`F`、その他の選択肢があるか）
  - 反映先: `person_demographics.gender`

- [ ] **役員が現行の役職一覧に登録されているか** — 登録されていない場合、移行時にどこから取り込むか
  - 登録されていれば設置組織がどうなっているかも確認する（現行は会社相当組織がない）
  - 反映先: `REQUIREMENTS.md` 6.4（会社相当組織の生成）

- [ ] **組織一覧に外部システムコードのフィールドがあるか** — bozuman コードは「タグ一覧」＝職能側にあった
  - ない場合、`org_external_code` テーブルを削除する
  - 反映先: `db/schema.sql`、`POC.md` 3章-14

- [ ] **組織一覧が経路を組織「名」で持っているか、組織「コード」で持っているか** — 移行時に親を特定できるかに直結
  - 名前で持っている場合、同名組織があると親が一意に決まらない（会社が違えば同名は起こりうる）
  - 反映先: `REQUIREMENTS.md` 6.2（組織階層の移行）

## B. 人事・労務に確認すること

運用ルールの確認。データを見ても分からないもの。

- [ ] **転籍時に社員番号（`employee_no`）が変わるか** — `person_id` は不変とするが、社員番号が会社跨ぎで変わるか
  - アルムナイ・再雇用時に番号を再利用するかも合わせて確認したい
  - 反映先: `REQUIREMENTS.md` 7章-1

- [ ] **休職を細分化する必要があるか** — 産休・育休・私傷病・介護を `employment_status.reason` で持つ方針
  - 独立区分にすべきものがあるか。判断基準は「その状態で在籍人員に数えるか（`is_active` が変わるか）」
  - 反映先: `employment_status_type` の初期データ

- [ ] **「管理職」の判定基準** — 女性管理職比率の算出に必要
  - 役職者（`position_holder`）で判定できるか、役職を持たない管理職相当がいるか
  - 後者なら `position_grade` だけでは判定できず、等級のような別軸が必要になる
  - 反映先: `SPEC.md` 3.5、`POC.md` 2章

- [ ] **同一役職に同時に複数人が就くか** — 共同部長のような運用があるか
  - ない場合、`position_holder` の `EXCLUDE` を `(person_id, position_id, period)` から `(position_id, period)` に変えて排他にする
  - 反映先: `db/schema.sql`

- [ ] **採用分析（内定承諾率等）が必要か** — 必要なら内定辞退の履歴を残す仕組みが要る
  - 現在は入社前を「雇用開始日が未来日の行」で表すため、辞退は行の削除になり履歴が残らない
  - 反映先: `SPEC.md` 3.8、`REQUIREMENTS.md` リスク19

- [ ] **人的資本開示で実際に出している指標** — 女性管理職比率・男性育児休業取得率・年齢構成のうちどれを出しているか
  - `person_demographics` に持つべき項目の確認になる（現在は性別・生年月日）
  - 反映先: `SPEC.md` 3.5

## 確認済み

同じ検討を繰り返さないための記録（`PROJECT.md` 5.2 の方針）。

- **役職階層の値** — 0 役員／1 本部長／2 副本部長／3 部長／4 副部長／5 チームリーダー。数字が小さいほど組織上の上位
- **副本部長・副部長の意味** — 「副本部／副部という組織の長」ではなく「**本部／部の No.2**」。同一組織に階層の違う役職が並ぶため、`org_layer` と `position_grade` は 1:1 対応しない
- **在籍状況の現行7区分** — 0 入社前／1 在籍／2 休職／3 退職／4 在職(外部)／5 休職(外部)／6 退職(外部)。「内部・外部」×「在籍・休職・退職」＋「入社前」の掛け算
- **在籍状況の「外部」の意味** — 業務委託・派遣などの雇用契約のない外部人材（グループ会社の社員ではない）
- **タグ（職能）の用途** — 開発組織メンバーの職能（フロントエンド／バックエンド／QA／PD マネジメント等）を組織ツリーとは別の横軸で管理するもの。「kintone 開発組織」と「全製品のフロントエンドエンジニア」のマトリクス管理
- **給与体系の中身** — 月給／年俸／日給／時給の分類のみ。**給与額は含まない**
- **労務系5項目の現行の格納場所** — 所定労働時間数・週の勤務日数・固定残業時間数・労働時間管理・給与体系はすべて「社員名簿(公開)」アプリ。現行で公開情報として扱われている
- **兼務工数** — HRCore のスコープ外。kintone 側で継続管理する（変更頻度が高い）
- **在籍出向** — 存在しない。会社跨ぎは転籍のみなので、雇用は同時に1社
