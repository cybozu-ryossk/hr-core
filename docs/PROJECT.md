## 1. プロジェクトの目的

人事データ基盤の目標は「人材マネジメント」を支える基盤となること。

人事データを収集し、中長期事業戦略から必要な人材を予測し、効果的な施策を素早く検討・実行し、継続的にモニタリングできる状態を理想とする。対象となる人材マネジメント領域は、採用・配置・評価・報酬・育成・代謝。

### 1.1 到達目標（成熟度の3軸）

人事データ基盤は、事業拡大に伴って増加する社員数・組織の複雑度に対応できるよう、3つの軸で成熟していく必要がある。

**A: データ基盤**
1. 分散・個別管理
2. 業務別データ管理
3. 人事マスタ中心のデータ統合
4. 全社員の人事データ活用基盤

**B: 業務効率・自動化**
1. 手作業中心
2. 部分自動化
3. 全体最適の自動化（システム連携・拡張性）

**C: データ分析**
1. 単年集計（現在の部門別離職率は？）
2. 経年比較（この3年での離職率推移は？）
3. 要因分析（離職率悪化の要因は？）
4. 予測分析（離職率は今後どれだけ変化するか？）

### 1.2 成熟度レベルと現在地

- **レベル1** 紙・属人管理 — 紙・Excel・個人PC に散在し人事情報が統合されていない
- **レベル2** 部分的デジタル化 — 勤怠・給与などが点でシステム化されているが、システム間がつながっていない
- **レベル3** 基幹人事システム整備 — 人事情報がひとつのシステムに集約されガバナンスが効いているが、分析や時系列管理は手作業に頼っている ← **サイボウズ現在地**
- **レベル4** データドリブン人事 — 人事データが時系列で蓄積され、組織・人材の分析が継続的に行える
- **レベル5** 戦略的人材マネジメント — 人事データが経営・事業戦略と統合され、シミュレーションや予測に基づき打ち手を意思決定できる

本プロジェクトは **レベル3 → レベル4（さらにレベル5）** への移行を目的とする。特に「時系列管理の手作業依存」の解消が中心課題。

### 1.3 レベル4/5 で実現したいこと

- **大量の人事異動・組織変更への対応**
  - 3,000人規模（現在の約2倍）を想定
  - 月間人事異動は平均 50〜80名/月
  - 組織階層は 5〜7階層（3,000人規模企業の一般論。サイボウズの実際の階層区分は5段階。`REQUIREMENTS.md` 3章参照）
  - 十分に自動化されていれば、少ない人員でオペレーションを回せる
- **部門レベルでの人事データ利用**
  - 定量データ（パフォーマンス・スキル）に基づく説明性の高い配置・評価判断
  - メンバーのコンディション変化に早く気づく
  - 適切な人員計画・スキル計画の策定、部門間でのリソース調整
- **経営計画と連動した人員計画**
  - 異動・離職予測も加味した計画
  - 必要なスキル・役割の可視化による採用・育成の重点検討
  - 適正な組織構造（階層・マネジメント人数）設計
  - 採用計画の再現性と精度の向上

## 2. 現状（As-Is）

### 2.1 システム構成

サイボウズでは基幹系・情報系システムの多くにノーコードツール（kintone）を利用しており、人事・労務領域の業務システムも大部分が kintone で構築されている。人事マスタ（グループ企業含む）と、それを参照する業務システムの多くが kintone ベース。

人事データ基盤は人事本部主導で構築され、必要な情報を情報システム本部に連携する仕組み。

### 2.2 関係者

- **人事インフラ部** — 人事マスタの整備
- **人事** — オンボーディング・採用・育成などの業務アプリを開発・運用
- **労務** — 勤怠・給与・福利厚生などの業務アプリを開発・運用
- **情報システム本部** — 各種ID・機材の管理、各種自動化の開発
- **その他各部門** — 部門業務アプリ、社内活動・アンケート実施時に人事マスタを参照

### 2.3 現行のデータ構成（kintone アプリ）

人事データの基盤となる「社員名簿」アプリは、公開/非公開を分けたうえでグループ全体の社員をマスタ管理している。

- **社員マスタ（非公開）** — グループ会社を含む（一部情報のみ）。原則として自分のレコードのみ参照可能。個人情報・緊急連絡先など
- **社員名簿（公開）** — グループ会社を含む。基本情報、現在の所属、拠点、働き方。配属履歴などの関連テーブルを参照
- **組織** — 組織コード、組織名、階層、責任者
- **役職** — 設置組織、役職名（例: 人事本部 本部長）、ラインマネジメントの役割（理想／業務／組織／人材／投資）

### 2.4 現行の運用実態

**配属管理アプリからマスタへの訂正を、ほぼ人力で行っている。**

配属履歴（配属管理アプリ）とマスタの現在値が二重管理になっており、同期は手作業。課題②（SSOT の維持難易度）の具体的な現れ方であり、以下の帰結を生んでいる。

- 訂正漏れによる不整合が構造的に発生しうる
- 現行データには期間の重複・ギャップ・参照欠損が存在する可能性が高い（移行時のクレンジング対象。`REQUIREMENTS.md` 6章参照）

### 2.5 現行構成の背景（なぜ kintone だったか）

サイボウズには「100人100通りのマッチング」という人事ポリシーがあり、これを人的資本経営における競争の源泉と位置づけている。この前提では、既製の人事 SaaS をカスタマイズするより、ノーコードツールをベースに内製開発するほうがコストメリットが大きいと判断した。

得られている価値は以下の通りで、**再構築後も維持すべき要件** として扱う（`REQUIREMENTS.md` 2章）。

- **人事施策を「あるべき」を前提に実行できる** — システムのデータモデルがボトルネックにならない
- **社内情報基盤が kintone であるため連携性が高い** — 業務システムだけでなく部門業務やアンケートでも社員番号キーで情報取得ができ、データが死蔵されずに最低限使える形で蓄積する
- **バックオフィス担当者のデータリテラシーが向上** — 基本的なシステム変更は部門主導で行われ、担当者が kintone 管理者として最低限の知識を習得している

※ 法改正に追従する必要があるシステムは専用 SaaS を利用。

### 2.6 現行で実現している固有要件

経営・組織戦略上の要求に応えるため、kintone ベースの設計で以下を内製実装している。

1. **兼務工数の表現**
   - 経営企画部より、人的コスト分析の高度化のため細分化された兼務割合の設定を要望
   - 例: 人事本部 — 労務チーム 50% / 人事関連システムチーム 30% / HR数値分析チーム 20%（合計100%になるよう管理）
   - → **HRCore のスコープ外。kintone 側で継続管理する**（`REQUIREMENTS.md` 1章参照）
2. **マトリクス組織の管理**
   - 開発本部より、貢献度をより適正に評価するため職能カットでの所属表現を要望（元は製品単位のピラミッド組織）
   - 職能ごとのマネジメントラインの管理・職能に従ったチーム表現の仕組みを開発
   - → HRCore の配属モデルで表現する（複数の配属を期間で持てる形）

苦労した点として、ノーコードツールであっても本番運用中アプリへの大規模改修は困難であり、影響範囲の把握に苦労したことが挙げられている。

## 3. 現行の課題（再構築の動機）

### ① 時系列データ管理

マスタデータはスナップショットで保持するため、時系列データは別途定期的に出力する必要がある（kintone 単体では range types 等がなく、直接時系列を扱えない）。結果、各種分析時に結合作業が必要になり工数が増大している。

→ **本プロジェクトの最重要課題。PostgreSQL 採用の主目的。**

### ② リレーション構造

kintone は厳密な RDB ではなく、ビュー・非同期のリレーションとなる。結果、人事データ基盤として同期性のある SSOT（Single Source of Truth）を維持するための運用難易度が上がっている（2.4 の人力訂正がその具体例）。

### ③ その他機能面の開発コスト

人事データ基盤に付随する複雑な機能要件が実装できておらず、一部を手作業でカバーしている。組織規模拡大に伴い作業工数が膨らんでいる。

- 組織図の作成 → HRCore では必須としない（現行流用可）
- 未来日の異動・組織変更の予約 → 期間モデルで構造的に解決
- 異動シミュレーション → 現状運用がないためスコープ外

## 4. 再構築の方針

技術構成の詳細は `SPEC.md`、スコープと要件は `REQUIREMENTS.md` に記載する。本章は「なぜこの構成を選んだか」を扱う。

### 4.1 基本方針

データ基盤部分を kintone から切り出し、**業務システム（kintone）はフロントエンド DB として利用する** 構成を目指す。

- 業務システム部分は、柔軟さを保つために引き続き kintone を利用する
- 人事データ基盤は PostgreSQL で構築し、時系列データを統合的に扱う
- 人事データ基盤と kintone の連携は、性能を考慮して **直接参照する仕組み（kintone の外部システムのアプリ化機能）** を採用する
  - 従来は API 連携でデータをレプリケーションする必要があったが、外部システムのアプリ化機能により現実的に履歴テーブルを扱えるようになった

### 4.2 kintone を残す理由

- 現場主導での業務アプリ改善サイクルを維持する（データリテラシー向上の効果を失わない）
- 社員番号キーでの全社的なデータ連携性を維持する
- 人事制度の柔軟性をシステム側で制約しない
- UI を内製する必要がなくなる（HRCore に管理画面を作らない）

### 4.3 YESOD 検討から PostgreSQL 内製への方針変更

一次情報（2026-03）の時点では HR 系 SaaS の YESOD を検討していた。時系列データを統合的に扱えること、組織図出力・未来日予約など内製コストが高い機能が揃っていることが採用理由だった。その後の検討で、以下の理由により PostgreSQL による内製構築に変更した。

**1. 利用規約とデータの取り扱い**

YESOD の利用規約上、入力データの取り扱いに社内規約と合わない箇所があった（入力した人事データが営業データ等として利用され得る）。人事データという性質上、この点は許容できない。

**2. API 仕様・UI の使いにくさ**

API 仕様が使いにくく、UI にも癖がある（フィールドやレコードの削除ができないなど）。内製したほうが利便性が高い。

**3. 構成上、SaaS の UI 部分が不要になる**

業務システム側を kintone UI で構成する前提のため、YESOD 側の機能のうち UI 部分がすべて不要になる。実際に使う機能に対してコストが割高になる。

**4. 中核要件が PostgreSQL の標準機能で満たせる**

扱いたいのは時系列データであり、PostgreSQL の期間クエリ（range types）で対応できる。

- range types / exclusion constraint により、有効期間を持つデータを DB の制約として表現できる
- 再帰クエリ（recursive CTE）で組織階層の展開ができる
- 未来日データを同一テーブルで自然に保持でき、未来日予約と as-of 参照を同じモデルで扱える
- 分析用途で標準 SQL / BI ツール / AI エージェントから直接扱える

**5. 社内クラウド基盤の活用**

社内にクラウド基盤が存在し、この資産を使えば運用管理コストを低く抑えられる。SaaS を利用する旨みが小さい。

**6. データ主権の維持**

データモデルを自社に保てる（SaaS へのデータモデルロックインを避ける）。6章のコスト性質論と整合する。

**残るトレードオフ**

YESOD 採用理由だった「組織図出力・未来日予約」は自前実装が必要になる。ただし検討の結果、コストは小さいと判断した。

- **未来日予約** — `valid_start` を未来日で登録し、参照側が基準日で判定すれば成立する。反映バッチ不要で実装コストは実質ゼロ
- **組織図** — 階層データを返すのは recursive CTE で足りる。描画 UI は kintone 側（外部システムのアプリ化）で実現できる。かつ組織図は必須機能ではなく、現行の仕組みをそのまま動かすこともできる
- **異動シミュレーション** — 現状の運用がないため落とす

### 4.4 ROI の正当化ロジック

人事システムの刷新はコストがかかる一方、ROI 算出と正当化の難易度が高い。現在の業務工数の改善効果だけではマイナス〜0の投資対効果になることもある。そのため「なぜ今やる必要があるのか」を長期的な時間軸で以下2点に整理して説明した。

**As-Is のまま組織が拡大した場合のリスク**
- 企業規模が増大した場合の業務工数増をシミュレーションし、早期に刷新することでコスト削減効果が最大化することを明示
- 現場担当者への属人化度合いの高まりを言語化し、刷新の有効性を論理的に説明

**To-Be で実現できる未来に対する投資**
- 目指すべき人事データ基盤（To-Be）を描き、人事インフラ高度化のプラス面を説明
- 生成AI によるビジネス環境の複雑性増加に対し、採用・育成分析の高度化を早い段階で行う必要性を訴求

## 5. PoC の位置づけと進め方

PoC の技術スコープ・検証項目は `POC.md`、設計内容は `SPEC.md` に記載する。

### 5.1 位置づけ

**PoC は Go/No-Go 判定ではない。** 刷新自体は決定事項であり、PoC はより良い構成をスクラップ&ビルドで探索し、設計を確定させるためのもの。定量的な性能基準は設けない。

### 5.2 進め方・体制

- **期間** — 8月中を目処に確認。厳密な期限や社内報告のタイミングはない
- **体制** — 開発は1名（プロジェクトマネージャー兼務）、AI エージェントを活用して実装。人事インフラ部が確認役
- **イテレーション** — 検証 PoC として作り、人事側と一緒に確認するサイクル
- **成果物** — 本ドキュメント群に記載した内容はすべて残す。作りながら最終的な構成図を残す形にする
  - スクラップ&ビルドで進めるため、**捨てた案とその理由も記録する**（同じ検討を繰り返さないため）

## 6. 参考: ツール選定フェーズ論（一次情報より）

人事データ基盤は組織拡大に伴うニーズ変化に合わせて成熟していく必要があり、採用するツールも合わせて変化することが求められる。規模に合わせた適切なツール選定を行わないと、管理工数増大または過剰投資になる可能性がある。

- **スプレッドシート** — 柔軟性重視、少人数管理。ビジネス・製品への投資優先。ガバナンス・属人性がネックで次フェーズへ
- **ノーコード** — 柔軟性を重視。機能の内製開発部分がネックで次フェーズへ
- **HR系SaaS** — 運用コストを重視。外部連携、複雑性への対応がネックで次フェーズへ
- **内製開発（HRIS）** — 拡張性・柔軟性を重視。人事領域を競争力の源泉とし積極的な人事戦略。人事とエンジニアが管理

サイボウズは「ノーコード」フェーズで機能の内製開発部分がネックになり、「内製開発」フェーズへ移行しようとしている段階。ただし**業務システム層はノーコードのまま維持するハイブリッド構成**を採る点が特徴。

### コストの性質の違い

- **導入コスト（データモデリング）** — ノーコード: 高 / HR系SaaS: 低
- **運用コスト（業務・運用）** — ノーコード: 低 / HR系SaaS: 高
- **移行コスト** — ノーコード: 低（構築したデータモデルはそのまま外部に移行できる）/ HR系SaaS: 高（データモデルが SaaS にロックインされる）

内製開発を正当化するメリットとして一次情報が挙げているのは以下。

- **データの主権を保てる** — SaaS に任せるとデータモデルがロックインされる。汎用 AI エージェントを利用した計画業務を行う上でも、データを柔軟でプレーンな状態に保つ要求は高まっている
- **積極的な人事施策を打てる** — 人事領域を競争力の源泉と捉え戦略的な施策を行うには、基盤の柔軟性・拡張性を保つ必要がある（例: 100人100通りのマッチング、アルムナイマネジメント）
- **現場主導の改善とデータリテラシー向上** — システムありきの業務にならず、バックオフィス部門もデータ構造を念頭に業務を組み立てる
